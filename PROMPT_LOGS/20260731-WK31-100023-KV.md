### 10:00:58 - Response

That message is from **nginx**, and it means:
> "Someone connected with a Host header nginx doesn't recognize — my default vhost returned this fallback message."

Even though `drupal.conf` was written to FSx during install-drupal (I saw the log line "wrote /etc/nginx/shared/sites-enabled/drupal.conf"), **nginx hasn't been reloaded to pick it up**.

## Why

Same class of problem as the DNS gap. `install-drupal-full` is the complete flow — it includes step 3: `reload-nginx`. But `install-drupal` (bare, which migrate-full-all's `AUTO=yes` invokes) doesn't reload nginx.

So:
- Vhost file is on FSx: ✓
- Nginx knows about it: ✗ (running config was loaded before the file existed)

## Fix — one command

```bash
cd ~/projects/cf-scalable-web
make reload-nginx ENV=sandbox
```

That SSMs into each nginx instance and does a graceful `nginx -s reload`. Nginx reads the shared config from FSx and picks up drupal.conf. Takes ~30 sec.

Then in your browser: **hard refresh** (Cmd+Shift+R) to skip Safari's cached response for that URL. You should get Drupal (either the front page or a login redirect).

## And another Phase D item

Same pattern as the DNS gap — install-drupal (bare) leaves the environment in an unusable state. install-drupal-full is the "actually works" superset. Cleaner design would be:
- `install-drupal` = install + publish-vhost + reload-nginx (leaves a WORKING Drupal, no DNS, no smoke-test)
- `install-drupal-full` = install-drupal + publish-dns + smoke-tests (leaves a WORKING + PUBLIC Drupal)

Then `AUTO=yes` triggering install-drupal gives you a functioning site. I'll add this to backlog after the immediate fix works. Fire reload-nginx and let me know.
