## Root cause

AWS CLI v2's `aws s3 sync` default is `--copy-props default`, which
preserves both metadata AND source object tags. Preserving tags means
calling s3:GetObjectTagging on the source. IAM authorization for that
action happens BEFORE the object's tag list is examined — so even
zero-tag objects fail the auth check. (Kurt verified in the S3 UI:
all failed objects show "Tags(0)".)

The CLI only invokes GetObjectTagging on some copies (multipart path,
larger objects), which is why the earlier hundreds of files copied
fine and only ~5 in the first batch failed. Would have gotten worse
as the sync worked through bigger files.

## Client-confirmed workaround

Client doesn't use S3 tags at all in this bucket. Switch sync's
--copy-props from the implicit default to `metadata-directive`:

  aws s3 sync ... --copy-props metadata-directive

That preserves user-defined metadata (Content-Type, Cache-Control,
Content-Disposition — critical for Drupal-served PDFs and images to
render inline in browsers) but skips the tag preservation step.
No GetObjectTagging call, no auth failure.

## Rejected alternatives

- `--copy-props none` — TOO aggressive. Also strips Content-Type, so
  PDFs would serve as application/octet-stream and browsers would
  download them instead of rendering inline. Would break the whole
  point of the migration.
- Grant s3:GetObjectTagging + s3:PutObjectTagging on both sides —
  works but requires two more CFN redeploys for zero client benefit,
  since the tags they'd preserve aren't used by anything.

## Idempotency — the ~few succeeded copies stay put

aws s3 sync is incremental (compares source last-modified + size to
target). The ~60 files that copied in the failed run are already in
the sandbox bucket; the re-run only transfers the ~6110 remaining
new/changed objects. No wasted work.
