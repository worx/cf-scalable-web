## Q5 answer: staging-bucket clone (recommended)

My honest read is **B (clone to staging bucket with lifecycle)**. Reasoning:

| Dimension | Option A (production bucket presign) | Option B (staging clone) |
|---|---|---|
| Storage cost | none extra | trivial (10 days × small PDFs) |
| Blast radius on URL leak | 7 days of access to a PRODUCTION file | 7-10 days of access to a file that's going away anyway |
| Ability to revoke | rotate signing key (heavy) | delete file from staging (surgical) |
| Compliance story | "we presign into prod" | "no production data leaves the private bucket" |
| Audit visibility | can't easily enumerate what's currently exposed | staging bucket IS the current-exposure list |

The extra ~15 lines of code + one lifecycle rule + one bucket buys you real security-posture wins. Standard AWS pattern for time-limited delivery.

**Decision to codify in the doc**: staging bucket, 10-day object lifetime, 7-day max presigned URL (so URL always expires before object). Lambda writes the "keep forever" copy to production PRIVATE bucket AND writes a copy to staging when large-file delivery is needed. Small PDFs stay production-only and get emailed as attachments (no URL needed).

## Q8 answer: Image Builder pipeline, monthly cadence + on-demand

My read: **Image Builder pipeline, monthly rebuild by default, on-demand trigger available**. Reasoning:

- **Consistent with existing pattern**. You already have Image Builder pipelines for nginx/php74/php83 AMIs. Adding a "latex-lambda" ECR-image pipeline reuses the operational muscle memory.
- **Ghostscript is the real driver.** Ghostscript has had several PDF-processing CVEs over the years (some serious — like `-dSAFER` bypasses). Monthly rebuild pulls fixes automatically. TeX Live CVEs are rare; Ghostscript CVEs happen.
- **Cost is negligible.** Image Builder pipeline runs cost pennies. ECR image storage costs pennies per GB per month.
- **Monthly cadence** is the sweet spot: weekly is over-eager (nothing usually changes), on-demand-only means CVEs go months without a rebuild.
- **On-demand trigger** covers the "new TeX Live release" or "Zac needs a new LaTeX package" cases — same as your existing `make build-ami-nginx` pattern.

Small caveat: Lambda container images live in ECR (not AMI). Image Builder DOES support ECR-container pipelines (added 2022). Same conceptual shape as the AMI pipelines you already run.

**Question that only you can answer**: is there budget/appetite for the Image Builder pipeline complexity right now, or does "build once, plan for a manual rebuild in ~6 months" get us to production faster with acceptable risk? For an MVP-to-production launch, that's a defensible trade-off too.
