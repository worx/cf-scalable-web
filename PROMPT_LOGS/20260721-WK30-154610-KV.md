### 15:46:32 - Response

Precise answer: it's a **no-op on the deploy-host itself** — no reboot, no rebuild, no image swap. It just:

1. Runs on your Mac (or wherever you kick `make` from — reads `~/.aws/credentials` via the `AWS_PROFILE`)
2. Sends an SSM command to the already-running deploy-host that does three things:
   - `git pull` in `/home/ubuntu/projects/cf-scalable-web/`
   - `install -m 0755` the new `refresh-env-config` script to `/usr/local/sbin/`
   - Same for `use-env` and the sudoers file
3. Prints the result

Takes about 5 seconds. The deploy-host EC2 instance is not restarted, replaced, or reconfigured — only three files at `/usr/local/sbin/` get updated in place.

**Why the extra step exists** — the deploy-host's `bootstrap.sh` originally *copied* these scripts from the git checkout into `/usr/local/sbin/` (rather than symlinking). So `git pull` alone updates the source in `/home/ubuntu/projects/cf-scalable-web/scripts/deploy-host/refresh-env-config` but leaves the *installed* copy at `/usr/local/sbin/refresh-env-config` stale. This target syncs them.

**How you'd invoke it:**
- **From your Mac:** `make refresh-deploy-host-scripts` (dispatches the SSM command; deploy-host doesn't need to be logged into)
- **From deploy-host itself** (once you're already SSM'd in): you could just do `cd /home/ubuntu/projects/cf-scalable-web && git pull && sudo install -m 0755 scripts/deploy-host/refresh-env-config /usr/local/sbin/refresh-env-config` — same result, fewer moving parts if you're already inside.

Then Step 1 continues with `sudo refresh-env-config sandbox` — that reads the SSM param and writes `/etc/worxco/envs/sandbox`.
