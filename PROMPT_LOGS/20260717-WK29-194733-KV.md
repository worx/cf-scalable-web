## The problem

`make dump-files` + `make dump-private` (jumpbox side) push tarballs to
S3, but nothing restored them onto sandbox FSx. Migrated Drupal served
data from prod but 404'd on every image, PDF, download — because
`file_managed` rows point to `public://` paths (i.e., FSx paths under
sites/default/files/) that only existed on prod's disk.

## The approach: atomic swap

Neither restore blocks the site — extract fresh to `.NEW.<UTC>` next to
the target, `chown/chmod` matching install-drupal.sh's `root:www-data`
u=rwX,g=rwX,o= pattern, then a single `mv` renames current out of the
way (to `.BAK.<UTC>`) and promotes `.NEW` into place. The "cutover" is
one directory rename — atomic on FSx (metadata-only, sub-second).

Backup policy matches migrate-db-all: `.BAK` is preserved by default
(KEEP_BAK=yes). Operator drops it manually when satisfied. KEEP_BAK=no
overrides for auto-cleanup.

## Six-phase flow (mirrors restore-mysql)

  1. Preconditions (root, tools, /var/www mounted, Drupal deployed)
  2. Confirmation (shows current size/count vs incoming tarball)
  3. Fetch tarball from S3 (cached; FORCE_DOWNLOAD=yes overrides)
  4. Extract to .NEW dir (`--strip-components=1` drops the top-level
     "files/" or "private/" prefix)
  5. Ownership + permissions
  6. Atomic swap + verify

Both scripts validate gzip magic bytes before extraction so a corrupt
S3 object fails clearly instead of leaving half-extracted state.

## New pieces

### migration/scripts/deploy-host/restore-files.sh
Target: /var/www/drupal/web/sites/default/files

### migration/scripts/deploy-host/restore-private.sh
Target: /var/www/drupal-private
