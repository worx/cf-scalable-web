### 21:44:06 - Response

That's exactly the `create indexes` spike I warned about — SBCL allocates a big sort buffer per index build, releases it back to the heap when the index completes. 5.5 → 6.6 → 5.7 GB is one index build's full lifecycle. Peak at 6.6 GB is a real data point.

**Updated memory-downsizing math:** we now have a measured peak of ~7 GB during index-build phase. That's within m7g.xlarge's 16 GB (with buffer pool ceiling brought down to ~5-6 GB), but I'd still want to see the peak across a few more runs (different table sizes, different index counts) before committing. One data point ≠ population statistic.

You're right about "close to the end" — pgloader's canonical order is: load rows (concurrent) → create indexes (also can be concurrent per `max parallel create index = 4`) → reset sequences → foreign keys → done. Index builds are the biggest late-phase work; sequences + FKs are quick. If you're seeing index-build memory patterns now, you're in the last 10-20% of the run.
