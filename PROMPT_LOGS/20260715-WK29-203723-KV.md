## Not a regression — this is by design

The deploy-host **never** auto-mounts FSx at boot. The `use-env <env>` script is what mounts `/var/www` — from `bootstrap.sh:503-530`:

- `use-env sandbox` writes an fstab entry AND `/etc/worxco/current-env`
- On the next boot, systemd-fstab-generator picks up the entry and mounts automatically
- Bootstrap's "Restore last active env mount" step re-invokes `use-env` if `current-env != NONE`, so the mount survives re-bootstrap without operator intervention

**Your fresh deploy-host is doing exactly what it's supposed to:**
- No prior `use-env` invocation on THIS instance → no fstab entry → no /var/www → no mount
- `/etc/worxco/current-env` is either missing or "NONE"
- Bootstrap.sh's line 526/529 message would have said "operator must run `sudo use-env <env>`" — check `/tmp/rebootstrap.log`

**To get the mount now:**
```bash
sudo use-env sandbox
df -h /var/www    # should now show the FSx mount
```

## Gap worth closing before destroy/redeploy

Our `/scripts/deploy-host/backup-state.sh` **doesn't back up `/etc/worxco/current-env`**. So even with a perfect auto-restore, every new instance forces the operator to remember what env was active and re-run `use-env`. Two-line addition to BACKUP_PATHS (and KNOWN_PATHS in restore-state.sh) fixes it:

```diff
   # --- AWS CLI config (NOT credentials - see header) ---
   "/root/.aws/config"
   "/home/ubuntu/.aws/config"
+
+  # --- Active env marker (drives bootstrap.sh auto-remount step) ---
+  "/etc/worxco/current-env"
```

After restore, bootstrap.sh's line 515-524 does the rest: sees `current-env=sandbox`, runs `use-env sandbox`, /var/www gets mounted automatically. Zero manual steps on instance replacement.
