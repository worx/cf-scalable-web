fix(install-drupal): export DRUPAL_DB_SCHEMA=public for post-swap drush calls

Latent bug from commit 704506b (tonight's settings.php schema=zinew fix)
finally triggered: fresh-install cycle failed on the pm:uninstall step.

Sequence:
1. drush site:install creates Drupal tables in Postgres schema `public`
   (drush's default; no schema override passed via --db-url)
2. install-drupal.sh replaces settings.php with env-driven config that
   defaults `'schema' => getenv('DRUPAL_DB_SCHEMA') ?: 'zinew'`
3. The export block AFTER the swap didn't include DRUPAL_DB_SCHEMA
4. drush pm:uninstall then reads settings.php → getenv returns false →
   falls back to 'zinew' → tables are in public, zinew is empty →
   drush fatal: "Command pm:uninstall was not found. Drush was unable
   to query the database."
5. Cascading migrate-full-all → migrate-db-all → AUTO=yes preflight
   FAILURE.

Fix: export DRUPAL_DB_SCHEMA="public" alongside the other env vars in
install-drupal.sh's post-swap block. That routes the script's subsequent
drush calls (pm:uninstall, verify) to the public schema where tables
actually live.

Process-scoped: this export lives only for the rest of the install-drupal
script. PHP-FPM workers keep reading the settings.php default of 'zinew'
via their boot-time env[] injection (configure-php.sh doesn't set
DRUPAL_DB_SCHEMA either) — and that's correct, because by the time real
HTTP requests hit PHP-FPM, pgloader has populated `zinew` with the
migrated production data. The window between install-drupal completing
and pgloader running is not user-facing (nobody browses sandbox mid-
migration).

Doesn't rebuild the AMI, doesn't touch any deployed state — just the
install-drupal.sh script. Recovery for tonight's failed run:
  # on deploy-host:
  cd ~/projects/cf-scalable-web && git pull
  cd migration
  make migrate-full-all AUTO=yes
The AUTO=yes preflight branch will retry install-drupal from scratch,
this time completing cleanly, then migration proceeds.
