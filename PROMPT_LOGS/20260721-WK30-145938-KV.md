Two separate things worth untangling:

## 1. The `--output truncated--` is from SSM, not the sync

`aws ssm get-command-invocation` caps `StandardOutputContent` at ~24 KB. Anything past that gets replaced with the literal string `--output truncated--`. The sync itself kept running past that point — we just can't see the tail of its output through SSM's return path. Full log is on the jumpbox at `/var/log/…` (script uploads to `s3://sandbox-migration-kv-worxco/logs/2026-07-21/sync-s3-media-*.log`); you can pull that for the complete story.

## 2. `Title and Date_10.pdf` was a **success**, not a failure

Look at the two prefixes in the log — they're different:
- `copy:` → succeeded
- `copy failed:` → failed with the tagging error

`Title and Date_10.pdf` shows as `copy:` (success). To spot-check tags on actually-failed objects, look at these five that hit `copy failed:`:

## 3. Why does the error still fire even when a file has no tags?

The `AccessDenied` on `s3:GetObjectTagging` happens at the **IAM authorization** step, *before* S3 decides whether the object actually has any tags to return. So even a zero-tag object triggers it — AWS never gets far enough to check. The AWS CLI decides whether to *call* GetObjectTagging based on the copy path (multipart vs single-PUT, `--copy-props` mode), not on any tag-presence hint.

So it's not really a "tags exist" issue — it's a "the CLI tried to preserve tags on a bucket where it doesn't have that permission" issue. Which is why `--no-preserve-object-tags` fixes it universally.

## Want me to make that fix?

One-line change in `sync-s3-media.sh` — add `--no-preserve-object-tags` to the `aws s3 sync` call. No IAM churn, no CFN redeploy, and the successful files that already copied stay put (sync is incremental — second run only retries the ~dozen that failed).
