feat(migration): Phase -1 preflight — verify Drupal installed on target

Two related fixes bundled — both prevent the "why did migration leave
Drupal WSOD'd" surprise Kurt hit on 2026-07-19:

## Fix A: restore-private preserves sandbox salt.txt across the swap

Live catch: `restore-private` atomic-swapped `/var/www/drupal-private/`,
losing sandbox's salt.txt (which was in the swapped-out dir). Drupal
booted with no hash_salt and threw "Missing $settings['hash_salt']".

Fix in `migration/scripts/deploy-host/restore-private.sh`:

- New env var `PRESERVE_FROM_BAK` (default: `salt.txt`) — space-separated
  list of files copied from .BAK back into the target dir after the
  atomic swap succeeds.
- Sandbox-managed files (salt.txt, and any future ones) survive prod's
  tarball unconditionally — cross-env sharing is wrong for these.
- Overwrites whatever the tarball provided (which is prod's salt, if
  present at all) — sandbox's version is authoritative.

## Fix B: Phase -1 preflight in migrate-db-all

Even with A in place, running migrate-full-all against a sandbox where
install-drupal.sh was NEVER run would still fail at unpredictable phases
(no drupal DB to rename, no settings.php, no salt.txt at all in .BAK,
etc.). Migration is a "swap contents" workflow; it needs a structural
foundation.

New Phase -1 in `migrate-db-all` runs a structural check via SSM on the
target deploy-host BEFORE Phase 0's destructive db-backup. Verifies:

  1. /var/www is mounted (env's FSx via use-env)
  2. /var/www/drupal/vendor/bin/drush is executable
  3. /var/www/drupal/web/sites/default/settings.php exists
  4. /var/www/drupal-private/salt.txt exists

If any fails, prints a "run make install-drupal ENV=<env>" hint and
bails BEFORE any destructive operation. Bypass with SKIP_PREFLIGHT=yes
(intended for known-good sandboxes where the check has a false negative).
