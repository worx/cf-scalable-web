# migrate-host — Ephemeral Migration Instance Design

## §1 — Instance Spec

| Family | vCPU | RAM | ~$/hr (us-east-1) | Notes |
|---|---:|---:|---:|---|
| m7g.xlarge | 4 | 16 GiB | 0.163 | Meets literal floor; tight for concurrent MariaDB + SBCL |
| **r7g.xlarge** | **4** | **32 GiB** | **0.214** | **Recommended** — memory headroom for "dialed up" tuning |
| c7g.2xlarge | 8 | 16 GiB | 0.290 | Extra vCPU under-used; RAM tighter than m7g |
| m7g.2xlarge | 8 | 32 GiB | 0.326 | Overkill on vCPU for I/O-bound workload |

**Recommend r7g.xlarge.** The Phase-2 hot path runs MariaDB and pgloader *concurrently* — pgloader reads from local MariaDB while streaming to RDS. Both are RAM-hungry: MariaDB wants 8 GiB InnoDB buffer pool for a fast import, SBCL wants 10 GiB heap after the "dial up." On m7g.xlarge (16 GiB total) that leaves ~-2 GiB for the OS after generous rounding — livable only if we tune both consumers down, which defeats the whole point of the new host. On r7g.xlarge, both get comfortable ceilings with 8-10 GiB slack.

vCPU: 4 is enough. Pgloader's wall time is dominated by (a) target RDS write speed and (b) local MariaDB read speed — both I/O-bound. Doubling vCPU on c7g.2xlarge gains nothing for a workload that never CPU-saturates the current 2-vCPU deploy-host.

**Trade-off to weigh:** if a future client migration hits a 20 GB DB (vs today's 2.5-4 GB zinew), r7g.xlarge stays sized right; m7g.xlarge would force a re-tune. Cost delta over m7g: $0.05/hr = ~$0.05 per ephemeral run.

**Root EBS: 40 GiB gp3, `Iops: 6000`, `Throughput: 250 MB/s`.** Extra provisioned IOPS + throughput above gp3 baseline (3000 / 125) cost ~$0.03 for a 1-hour run. Sizing math: ~5 GiB OS + ~3 GiB staged dump + ~6 GiB imported `/var/lib/mysql` + working temp ≈ 15 GiB used; 40 GiB gives 25 GiB slack. Why provisioned IOPS matters: **today's real bottleneck is InnoDB flushing to 3000-IOPS-capped root EBS during `mysql &lt; dump.sql`.** Doubling IOPS is the cheapest wall-time win in the whole plan.

**Swap: 0.** With 32 GiB and the tuning ceilings below, swap is a footgun (thrash &gt; OOM). If we ever OOM, grow the instance, don't paper over it with swap.

## §2 — Tuning Targets

### MariaDB — new drop-in `/etc/mysql/mariadb.conf.d/99-migrate-host.cnf`

```ini
[mysqld]
# Sized for r7g.xlarge (32 GiB). Leaves ~10 GiB for pgloader SBCL + ~8 GiB slack.
innodb_buffer_pool_size          = 8G
innodb_buffer_pool_instances     = 4
innodb_log_file_size             = 1G
innodb_log_buffer_size           = 64M
innodb_flush_log_at_trx_commit   = 0   # bulk-load; flush once/sec
innodb_doublewrite               = 0   # throwaway DB, skip DW buffer
innodb_flush_method              = O_DIRECT
innodb_io_capacity               = 2000
innodb_io_capacity_max           = 4000
innodb_buffer_pool_dump_at_shutdown = 0
innodb_buffer_pool_load_at_startup  = 0
sync_binlog                      = 0
skip_log_bin                          # no binlog at all
max_allowed_packet               = 512M
performance_schema               = OFF # save ~500 MB RAM for buffer pool
```

Rationale: the `flush_log_at_trx_commit=0` + `doublewrite=0` + `sync_binlog=0` + `skip_log_bin` quartet is the standard "bulk-load; durability doesn't matter" recipe — turns a synchronous 3000-IOPS-bound workload into a mostly-async one. `innodb_log_file_size = 1G` (up from default 96M) means far fewer checkpoint stalls during the multi-GB import. `O_DIRECT` avoids double-caching once buffer pool is 8 GB.

### `restore-mysql.sh` — wrap the mysql invocation (Phase 6, line ~283)

```bash
{
  echo "SET SESSION FOREIGN_KEY_CHECKS = 0;"
  echo "SET SESSION UNIQUE_CHECKS      = 0;"
  echo "SET SESSION AUTOCOMMIT         = 0;"
  echo "SET SESSION SQL_LOG_BIN        = 0;"
  cat "$DUMP_LOCAL_PATH"
  echo "COMMIT;"
} | mysql -h 127.0.0.1 -u "$LOCAL_DB_USER" -p"$LOCAL_DB_PASS" "$LOCAL_DB_NAME"
```

Rationale per flag:
- `FOREIGN_KEY_CHECKS=0` — skip FK validation on every insert (dump ordering may violate temporarily; final state is consistent).
- `UNIQUE_CHECKS=0` — skip unique-index probes (dump is unique by construction).
- `AUTOCOMMIT=0` + trailing `COMMIT` — one transaction across the whole import; InnoDB doesn't fsync per-statement.
- `SQL_LOG_BIN=0` — belt-and-suspenders with server-level `skip_log_bin`.

Guard the wrapping with a `[ -f /etc/worxco/migrate-host-marker ]` check so restore-mysql.sh stays safe when run on legacy deploy-host during rollout.

### pgloader — edit `migration/pgloader/zinew.load.tmpl` WITH block

| Knob | Old | New | Why |
|---|---:|---:|---|
| `batch rows` | 500 | 5000 | 10× fewer INSERT round-trips to RDS |
| `batch size` | (unset) | 100 MB | Hard cap on per-batch RAM — protects against a wide-row table blowing past the row-count estimate |
| `prefetch rows` | 500 | 5000 | Match batch so MariaDB reads don't stall behind Postgres writes |
| `workers` | 2 | 4 | Matches pgloader's own default (reader/writer/formatter/buffer) |
| `concurrency` | 1 | 4 | **Biggest wall-time win** — 4 tables imported in parallel vs strictly serial today |
| `max parallel create index` | (unset) | 4 | Parallel index builds after loads — matters for large tables |
| `PGLOADER_HEAP_MB` | 4096 | 10240 | SBCL heap: 4 concurrent tables × ~150-250 MB in-flight + working set. 10 GiB = 5× headroom |

**Which knob matters most:** `concurrency` — by a mile. Everything else is a linear speedup on top of that. If Kurt wants to stay conservative on the first run, `concurrency=2, workers=4, batch rows=2000, heap=6144` still captures most of the win and proves the new host works without pushing the envelope.

**Expected wall-time shape:** restore-mysql 10-15 min → 3-5 min; pgloader 30 min → 8-12 min. Combined savings ~25-30 min, matching the stated goal.

### Peering — recommend inline SG ingress inside cf-migrate-host.yaml

The peering **connection** and **routes** in cf-deploy-peering.yaml are shared (only one peering per VPC pair anyway) — those stay unchanged. What migrate-host needs is four `AWS::EC2::SecurityGroupIngress` resources granting FSx (2049 + 111), RDS (5432), and Valkey (6379) from the migrate-host SG. Put those **inside cf-migrate-host.yaml**, not in a separate peering stack:

```yaml
FSxIngressNFSFromMigrateHost:
  Type: AWS::EC2::SecurityGroupIngress
  Properties:
    GroupId: !ImportValue
      Fn::Sub: '${EnvironmentName}-fsx-sg-id'
    IpProtocol: tcp
    FromPort: 2049
    ToPort: 2049
    SourceSecurityGroupId: !Ref MigrateHostSecurityGroup
    Description: NFS from migrate-host (via VPC peering)
# … same shape for FSx portmapper 111, RDS 5432, Valkey 6379
```

**Why inline:** the ingress rules reference the migrate-host SG. If they lived in a separate stack, tearing down migrate-host would fail (dependent resource still references its SG). Inlining makes deploy/destroy lifecycle-atomic. Same dependency graph deploy-host has today (cf-deploy-peering must be deployed first for the ENV).
