### 12:38:40 - Response

Found the actual issue — nothing to do with jumpbox rebuild. Look at the shell prompt on your terminal:

```
ubuntu@ip-172-31-16-49:~/projects/cf-scalable-web/migration%
```

You're running `make sync-s3-media` **from the deploy-host**. The dispatcher does:

```bash
aws --profile ZoningInfoAdmin cloudformation describe-stacks --stack-name cf-migration-jumpbox
```

The deploy-host only has the **sandbox** IAM instance role. It has zero credentials for the prod account (`ZoningInfoAdmin` profile doesn't exist there). So the describe-stacks call returns empty → "stack not deployed" error, even though the stack is UPDATE_COMPLETE with `JumpboxInstanceId = i-0616b051563227381`.

Verified from Mac just now — stack exists, output key is exactly `JumpboxInstanceId`, matches what the dispatcher expects.

## Fix — run from Mac, not deploy-host

The `sync-s3-media` target is Mac-only by design (same as the other cross-account migration ops: dump-mysql, dump-files). The three-hop chain is:

```
Mac (has ZI-Sandbox + ZoningInfoAdmin profiles)
 → S3 (uploads sync-s3-media.sh into sandbox migration bucket)
 → SSM send-command → prod jumpbox (uses its IAM instance role for cross-account write to sandbox media bucket)
```

Deploy-host has no role in this flow — it's for **sandbox-side** ops (restore-mysql / run-pgloader / restore-files).

**Run this from your Mac:**

```bash
cd ~/projects/cf-scalable-web/migration
make sync-s3-media
```

## Should the tooling be more helpful about this?

Right now the dispatcher gives a wrong-cause error message ("stack not deployed") when the real cause is "you're on the wrong host." Two small ergonomic fixes worth doing:

1. **Detect the case explicitly** — at the top of `_ssm-run-jumpbox.sh`, if `aws --profile ZoningInfoAdmin sts get-caller-identity` fails, error with:
   > "This target must be run from your Mac (needs ZoningInfoAdmin AWS profile for prod-account access). Detected: no ZoningInfoAdmin profile available. Current identity: <sts output>."
2. **Or Makefile-level guard** — refuse Mac-only targets from the deploy-host by checking `[ -f /etc/worxco/current-env ]` (deploy-host marker) and erroring with the same message.

Want me to add one of those? Small, safe change — worth 10 minutes to avoid this same confusion next time.
