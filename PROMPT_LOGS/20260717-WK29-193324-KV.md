fix(db): db-delete-backup needs transient elevation to DROP DB owned by drupal_user

Live test on the sandbox deploy-host revealed the same ownership gotcha
db-backup.sh and db-restore.sh already handle: DROP DATABASE requires
the caller to be the DB's OWNER, but `psql-env` connects as dbadmin
(RDS master), and backup DBs are owned by drupal_user (or whatever the
env's app user is).

    make delete-db-backup ENV=sandbox SELECT=1
    Type 'yes' to continue: yes
    === dropping drupal_backup_20260717_201352 ===
    ERROR:  must be owner of database drupal_backup_20260717_201352

## Fix

Apply the transient elevation pattern used elsewhere in this family
of scripts:

  1. Source /etc/worxco/envs/<env> to get APP_USER (DRUPAL_DB_USER)
  2. GRANT $APP_USER TO dbadmin (dbadmin joins the app-user role)
  3. For each backup DB:
       ALTER DATABASE <name> OWNER TO dbadmin;  (take direct ownership)
       DROP DATABASE <name>;                    (now permitted)
  4. REVOKE $APP_USER FROM dbadmin (via EXIT trap — runs even on
     failure, script kill, Ctrl-C, whatever)

The EXIT trap is set BEFORE the GRANT, so we never leave a permanent
role membership behind — even if the script dies partway through.

## Failure handling

Each DROP is its own psql invocation so a single failure (e.g., active
connections) doesn't halt the batch. On failure, we best-effort restore
ownership from dbadmin back to APP_USER — otherwise a failed DROP
would leave a dbadmin-owned DB drifting around. The recovery ALTER is
harmless if ownership hadn't been changed yet.
