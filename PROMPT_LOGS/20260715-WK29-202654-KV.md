## 1. run-pgloader needs restore-mysql first

Correct — `run-pgloader` even fails-fast checking that local `zinew` MariaDB has tables. Sequence is:

```
dump-mysql        (prod → S3, from jumpbox)
restore-mysql     (S3 → local MariaDB scratch, on deploy-host)

```

Whether to bundle them into a `make migrate-db` uber-target is a taste call. My preference is keep them separate — each is destructive in different ways, and interstitial verify steps ("does the S3 dump match prod expectations?", "did restore-mysql land the right table count?") are worth the operator eyeballing before proceeding. Not scope-creeping this unless you want it.

## 3. DB-only restore hypothesis — mostly right, three real caveats

Your reasoning is solid. Drupal lives on FSx (code + files) + RDS (data) + Valkey (cache). Compute reads from all three. Swap RDS content underneath a running site, keep the other layers stable, site keeps running.

**Where it will actually bite you:**

**A. Module presence mismatch (hard failure).** Prod's `key_value` and config tables list every module currently enabled in prod. If prod has any module enabled that isn't installed under `web/modules/` on FSx, Drupal will WSOD or throw a "module not found" fatal on the next request. Before the swap, compare:

```bash
# What prod thinks is enabled (from the fresh restore in MariaDB scratch)
mysql -uworxco -plocalscratchpass -h127.0.0.1 zinew -e "
  SELECT name FROM config
  WHERE name = 'core.extension'
" # then decode the serialized blob
```

vs. what's actually on FSx (`ls web/modules/contrib/`, `ls web/modules/custom/`). Anything in the DB but not on FSx is a blocker.

**B. Cache backend stale (soft failure — visible weirdness).** Valkey/ElastiCache still has cached objects keyed to the sandbox pre-swap state. Post-restore run `drush cr` from deploy-host against sandbox env. If that's not enough, flush Valkey directly. Otherwise: mangled render arrays, stale menus, blocks referencing dead entities.

**C. Broken file references (soft failure — visible in UI).** Every `file_managed` row points to `public://` or `private://` paths that resolve to FSx. Sandbox FSx doesn't have prod's uploads. Every image/download in a node body → 404. Fine for "does Drupal boot?" testing, ugly for "does anything actually look right?" testing. If you want the full picture, `make dump-files` + `make dump-private` + restore them to FSx too.

**Small caveats worth naming (not blockers):**

- **Maintenance window.** pgloader with `include drop` drops the schema mid-run. For those ~30-90 seconds, Drupal requests fail. Sandbox is probably-just-Kurt so meh, but put Drupal in maintenance mode first if you care (`drush sset system.maintenance_mode 1`).
- **Sessions invalidated.** Everyone gets logged out. Not a problem, worth expecting.
- **Site name in header shows prod's.** Cosmetic. Sandbox banner override in settings.php doesn't help here since site_name is in DB.
