### 15:13:17 - Response

Your thesis is right. The failure signature confirms it:

- **DNS resolved fine** (`3.224.240.134 44.207.47.234` are shown)
- **Pinned-IP curl returned 200** (proves ALB/cert/nginx/Drupal all work)
- **DNS-based curl returned HTTP 000** (couldn't connect)

Same IPs, same site, same request — the ONLY difference is DNS-based vs pinned-IP. `dig` bypasses OS-level caches (systemd-resolved on the deploy-host), curl goes through `getaddrinfo()` which uses them. Between `dig` running (which primed the cache) and curl running (which used it), something transient — likely the OS resolver briefly serving a stale IPv6 answer or an IP from a previous ALB — bit us. By the time you got back to your Mac 10+ minutes later, everything had converged.

## Recommended fix — retries with backoff

Cleanest fix: add 3 attempts with 15-second sleeps to `smoke-test-public`. First attempt might fail transiently; second or third almost always succeeds after the resolver catches up. If all 3 fail, THEN report failure (a real problem). Total worst-case delay: 30 seconds added to a successful smoke test — trivial.

Alternative — pre-flush the OS resolver cache at the start of the smoke-test (`sudo resolvectl flush-caches` on Linux, `sudo dscacheutil -flushcache` on Mac). Belt-and-suspenders against negative-cache carryover.

I'd do **both** — resolver flush + retries. Kills two failure modes cleanly.

Want me to implement that now? Small change to `scripts/smoke-test-public.sh`. Then future rebuilds won't false-fail on this. Or if you'd rather just retry `make smoke-test-public` manually when it hits this, that's fine too — the underlying system is working.
