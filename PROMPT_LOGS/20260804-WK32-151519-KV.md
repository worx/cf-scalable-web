fix(smoke-test-public): OS-detect resolver flush + 3-retry backoff on curl

Two hardening fixes for the transient-DNS false-fail Kurt hit after a
fresh destroy-all → deploy-all → migrate-full-all cycle:

Symptom: smoke-test-public reported HTTP 000 (curl couldn't connect)
immediately after migrate-full-all finished. But `dig` inside the same
target resolved cleanly, and the diagnostic `--resolve`-pinned curl
returned 200 — proving the site itself was healthy. 10 minutes later
Safari worked fine. Real cause: transient DNS/ALB/target-health
convergence race — one lookup gets a stale IP or the resolver briefly
serves cached-negative, curl connects to nothing, everything settles
seconds later.

Fixes:

1. Pre-flush the OS resolver cache at start of the target. OS-detects:
   - macOS: dscacheutil -flushcache + killall -HUP mDNSResponder
   - Linux (systemd-resolved): resolvectl flush-caches
   - Linux (older systemd): systemd-resolve --flush-caches
   - Unknown: one-line warning, don't fail
   All best-effort via sudo -n (no password prompt) with 2>/dev/null
   || true so a broken sudo config never blocks the test.

2. Wrap the DNS-based curl in a 3-attempt loop with 15s backoff
   between failed attempts. Falls through to the existing status-code
   handler with the final HTTP value. Worst-case extra delay on a
   successful test: 0 seconds (first attempt succeeds). Worst-case on
   a failing test: 30 seconds. Trivial cost, kills the flake.

3. Fix hardcoded "your Mac's resolver" diagnostic → "your OS
   resolver". Yesterday's failure was on the Linux deploy-host, and
   the message was misleading.

Files Modified:
- Makefile (smoke-test-public target only)
