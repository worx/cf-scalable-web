### Step-by-step

**Step 0** — Verify `flysystem_s3` module is actually present in your sandbox codebase (probably yes if this came from a React2 clone, but let's not assume):

```bash
make ssm-deploy-host
ls -la /var/www/drupal/web/modules/contrib/flysystem*     # module code present?
grep -A1 '"require"' /var/www/drupal/composer.json | grep -i flysystem
grep -i flysystem /var/www/drupal/composer.lock | head -5   # composer-registered?
# Also check it's ENABLED in the current DB:
psql-env sandbox -d drupal -c \
  "SELECT name FROM zinew.key_value WHERE collection='system.schema' AND name LIKE 'flysystem%';"
# (or whatever schema the sandbox DB uses — 'public' if pre-migration)
```

If flysystem_s3 isn't installed → we have to composer-install it (couple of minutes, no downtime).

**Step 1** — Refresh env-config on deploy-host so `AWS_S3_BUCKET` gets written:

```bash
make refresh-deploy-host-scripts   # get the new refresh-env-config binary on deploy-host
make ssm-deploy-host
sudo refresh-env-config sandbox
grep AWS_S3_BUCKET /etc/worxco/envs/sandbox
# Expected: export AWS_S3_BUCKET=sandbox-drupal-media-kv-worxco
exit
```

**Step 2** — Add the flysystem block to running `settings.php`. Since re-running `install-drupal.sh` would wipe your DB, we insert it manually. The block to append (matches the template):

```php
$_media_bucket = getenv('AWS_S3_BUCKET')
  ?: (getenv('ENVIRONMENT_NAME') . '-drupal-media-kv-worxco');
$settings['flysystem'] = [
  's3' => [
    'driver' => 's3',
    'config' => [
      'region' => getenv('AWS_S3_REGION') ?: 'us-east-1',
      'bucket' => $_media_bucket,
    ],
    'cache' => TRUE,
  ],
];
```

I can put this in a small script `scripts/deploy-host/inject-flysystem-config.sh` that does the append idempotently (checks for a marker, appends the block, backs up first) — that's the right home for this since we may need it again on staging when the time comes. Want me to write that?

**Step 3** — Get PHP-FPM to see `env[AWS_S3_BUCKET]`. Two ways:
- Cleanest: rebuild PHP-FPM AMI (bakes in the new `configure-php.sh`), cycle the ASG. That's the "real" fix but a bigger change.
- Quick: SSM one-liner into each PHP-FPM instance — append `env[AWS_S3_BUCKET] = "sandbox-drupal-media-kv-worxco"` to its pool config and reload FPM. Effective immediately, but gets lost on next instance rotation until AMI is rebuilt.

For test-migrating in the near term, the quick path is fine — AMI rebuild can come after you're satisfied the migration works end-to-end.

**Step 4** — Smoke-test:

```bash
# In the deploy-host or from SSM to a PHP instance:

echo "AWS_S3_BUCKET=$b\n";
$c = new Aws\S3\S3Client(["region" => "us-east-1", "version" => "latest"]);
$r = $c->listObjectsV2(["Bucket" => $b, "MaxKeys" => 3]);
foreach ($r["Contents"] as $o) echo "  " . $o["Key"] . "\n";
'
```

That confirms PHP-FPM sees the env var AND the IAM instance role can talk to S3. If both true, the DB migration is the only step left to actually see prod PDFs render.
