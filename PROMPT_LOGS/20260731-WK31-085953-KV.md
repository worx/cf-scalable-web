## What we did (SOA change)

Lowered SOA MINIMUM on `envs.zoning-info.com` from Route 53's default
86400 (24h) to 300 (5 min). SOA MINIMUM is what resolvers use as the
negative-cache TTL per RFC 2308 — an NXDOMAIN answer sticks in caches
for that duration. 24h was bad for a zone hosting sandbox/staging
records that go through destroy-all → deploy-all cycles.

The change was made directly via aws route53 change-resource-record-sets
(no CFN template owns the SOA today). Result:
    OLD: 1 7200 900 1209600 86400
    NEW: 2 7200 900 1209600 300   (serial auto-bumped)

## The "publish-dns early" insight (Kurt, 2026-07-31)

Currently publish-dns runs LATE in the deploy flow — after install-drupal
or manually after migrate-full-all. That means the 5-min negative-cache
window BEGINS when the operator is ready to test.

Better shape: run publish-dns the moment the ALB is up (mid-compute
phase, well before install-drupal or migration). The DNS record
doesn't need Drupal installed — it just needs the ALB to exist. If
we publish early, by the time install + migrate finish 1-2 hours
later, the 5-min negative cache has long expired and the URL just
works.

Also: verify SOA MIN is 300 as an idempotent preflight — if someone
recreates the zone and it drifts back to 86400, our automation would
still work (slowly) but the operator would want to know so they can
UPSERT it back.

Both captured under a new "Route 53 / DNS" section at the top of
phase-d-backlog.md. When Phase D work begins, this is one of the
higher-value fixes: it eliminates the 5-min "why isn't my URL
working" confusion after every rebuild.

## Yes — your idea is exactly right, and it's the cleaner architecture

Here's why it works and how it'd fit:

**The DNS record doesn't need Drupal.** It just needs the ALB. The ALB is up ~15 min into a deploy-all (mid-compute phase). Install-drupal + migrate-full-all is another 60-120 min after that. If publish-dns fires when the ALB comes up, then:

- **T+15 min:** ALB ready → publish-dns → 5-min negative-cache window BEGINS
- **T+20 min:** Negative cache expired everywhere. DNS is now serving fresh answers.
- **T+90 min:** Install + migration done. Operator opens Safari → **immediate resolution**. No "wait 5 min" step.

**Where to wire it:** two candidate places:

1. **Inside `deploy-compute-alb` target's tail** — cleanest technically (publish happens as soon as the resource that DNS needs to point at exists), but couples ALB deploy to DNS logic.
2. **New track in `deploy-all-parallel.py`** that depends on `alb` — declarative, matches the existing pattern (each track owns one thing, deps drive ordering).

I'd go with **#2** — a `dns` track that:
```python
"dns": {"deps": ["alb"], "label": "dns", "name": "Route 53 alias + SOA preflight",
        "cmd": "make publish-dns ENV={env} SOA_PREFLIGHT=yes"}
```

And the SOA preflight is what you described: check the zone's SOA MIN. If 86400, UPSERT to 300 and warn. Idempotent, self-healing if the zone gets recreated.

## Captured for Phase D — full write-up in `docs/memory/phase-d-backlog.md`
