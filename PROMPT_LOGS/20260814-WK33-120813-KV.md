## 1. Drupal settings pattern — `settings.local.php` is exactly right

Drupal's standard convention is:

- **`sites/default/settings.php`** — committed to git; baseline config; the "checked-in defaults." At the end of this file there's a stanza (usually commented; uncomment for the pattern):
  ```php
  if (file_exists($app_root . '/' . $site_path . '/settings.local.php')) {
    include $app_root . '/' . $site_path . '/settings.local.php';
  }
  ```
- **`sites/default/settings.local.php`** — NOT committed to git; environment-specific overrides. Loaded last, so it wins over `settings.php`.

The right storage bucket in the PHP array is **`$settings[...]`** (not `$config[...]`).
- `$settings[]` = infrastructure/environment config, unavailable via admin UI, meant for site-builders/devops. Perfect for AWS bucket names, IAM roles, feature thresholds. Examples in Drupal core: Redis config, memcached hosts, hash salt path.
- `$config[]` = runtime Drupal config overrides (per-env variants of Drupal-entity config). Wrong fit here.

There's no built-in "peak" or "custom settings" bucket — `$settings[]` is where custom infra config lives. Nest under a namespace to avoid collisions:

```php
// In settings.php (committed defaults):
$settings['worxco']['lambda_latex'] = [
  'input_bucket'         => 'sandbox-latex-input',
  'production_bucket'    => 'sandbox-latex-production',
  'staging_bucket'       => 'sandbox-latex-staging',
  'max_inline_bytes'     => 5 * 1024 * 1024,     // 5 MB — email-attach vs presign-URL threshold
  'presigned_url_ttl'    => 7 * 86400,           // 7 days
  'lambda_invoke_url'    => 'https://<api>.execute-api.us-east-1.amazonaws.com/prod/latex',
  'lambda_region'        => 'us-east-1',
];

// In settings.local.php (per-env overrides, NOT committed):
$settings['worxco']['lambda_latex']['input_bucket']      = 'zac-dev-latex-input';
$settings['worxco']['lambda_latex']['production_bucket'] = 'zac-dev-latex-production';
$settings['worxco']['lambda_latex']['staging_bucket']    = 'zac-dev-latex-staging';
$settings['worxco']['lambda_latex']['lambda_invoke_url'] = 'https://<dev-api>.../latex';
```

Access from PHP:
```php
$cfg = Settings::get('worxco')['lambda_latex'];
$bucket = $cfg['input_bucket'];
```

## 2. Presigned URL — direct AWS SDK, no intermediate Lambda

Definitively **direct SDK call from Drupal's PHP.** Reasoning:

- Presigned URL generation is a **local math operation** — HMAC-SHA256 of the URL fields using the IAM credentials. No AWS API call is made; the SDK computes it entirely client-side. Round-tripping to Lambda just to get a signature would be wasteful.
- Drupal almost certainly already loads `aws/aws-sdk-php` via Composer (for s3fs/flysystem media). If not, adding it is a one-line `composer require`.
- Drupal's PHP-FPM instance role can be granted `s3:GetObject` on the staging bucket via IAM; no static keys needed.

**Snippet to hand Zac:**

```php
use Aws\S3\S3Client;

$cfg = \Drupal\Core\Site\Settings::get('worxco')['lambda_latex'];

$s3 = new S3Client([
  'version' => 'latest',
  'region'  => $cfg['lambda_region'],
  // Credentials auto-resolved from IAM instance role — no keys needed.
]);

$cmd = $s3->getCommand('GetObject', [
  'Bucket' => $cfg['staging_bucket'],
  'Key'    => $stagingKey,   // e.g. "reports/2026/08/report-12345.pdf"
]);

$request = $s3->createPresignedRequest($cmd, '+7 days');
$presignedUrl = (string) $request->getUri();
```

**IAM permission Drupal's role needs:**
```json
{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::sandbox-latex-staging/*"
}
```

No AWS API call fires. `createPresignedRequest` returns the URL synchronously. That URL is what goes in the email.
