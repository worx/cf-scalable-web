Your memory's right — this is the key insight that unlocks the simplest solution.

## How dump-all actually works today

1. `make dump-all` runs on Mac or deploy-host — it's **just an orchestrator**
2. `scripts/_ssm-run-jumpbox.sh` uploads the dump-*.sh scripts to the sandbox migration S3 bucket
3. `aws ssm send-command` tells the **jumpbox in the prod account** to fetch those scripts from S3 and run them
4. The jumpbox does ALL the real work: mysqldump → S3, tar codebase → S3, tar files → S3, tar private → S3
5. Deploy-host / your Mac just polls SSM for completion

The jumpbox already has:
- Cross-account S3 write to the sandbox migration bucket
- Prod Secrets Manager read for the DB password
- Read access to the prod filesystem (codebase, files, private)

**So the deploy-host being up or down is irrelevant.** The jumpbox is the whole story.

## Options, ranked by complexity

### Option A: cron on the jumpbox (simplest) — MVP recommendation

- One-time setup: install a cron entry on the jumpbox + install a wrapper script
- Wrapper: `aws s3 sync s3://sandbox-migration-kv-worxco/scripts/ /opt/dump-scripts/ && /opt/dump-scripts/dump-all-nightly.sh`
- The sync-first pattern keeps jumpbox scripts fresh; you `make push-scripts-to-jumpbox` when you update anything
- OR: skip the sync entirely and bake scripts into jumpbox via CFN userdata + rebuild jumpbox when scripts change
- Failure: pipe wrapper output to SNS topic → email to you

Pros: zero new AWS services, uses what already exists, one file to maintain (the cron wrapper).
Cons: script freshness requires a manual push (or accepts staleness).

### Option B: EventBridge → Lambda → SSM SendCommand → jumpbox

- EventBridge rule with cron schedule
- Lambda (in prod account, same as jumpbox — no cross-account IAM)
- Lambda invokes `ssm:SendCommand` targeting jumpbox
- Command payload: same as what your Mac invokes today
- Lambda's runtime failures → CloudWatch → alarm → SNS

Pros: zero jumpbox-side maintenance, scripts stay in the current repo/S3 flow, centralized observability.
Cons: 3 new CFN resources (rule + Lambda + IAM role), Lambda code to maintain, a bit heavier.

### Option C: EventBridge Scheduler → SSM SendCommand (no Lambda)

- Newer EventBridge Scheduler can directly invoke SSM APIs without Lambda
- Same shape as B but Lambda-less
- Payload is embedded in the schedule config (rigid — schedule updates require re-deploy)

Pros: fewer moving parts than B.
Cons: less flexibility (can't do conditional logic), payload rigidity.

### Option D (your idea): Lambda that boots deploy-host, runs, tears down

Not needed since deploy-host isn't actually the worker — you skip a whole tier of complexity.

## My recommendation

**Start with Option A** (cron on jumpbox). MVP-simple, matches what a human would type, no new AWS services. Scripts stay in the repo, get pushed to S3 by an existing `dump-all` invocation once (or add `make push-jumpbox-nightly-cron` to install both the cron and a script-sync mechanism).

Failure notification via a simple `| aws sns publish --topic-arn ...` in the wrapper if any dump step fails. You get an email when a nightly dump fails; silence = success.

**Graduate to Option B later** if:
- You end up with many scheduled prod-side jobs and want a common scheduling plane
- You want the observability boost of CloudWatch metrics + alarms on Lambda invocations
- Script-freshness maintenance becomes a real annoyance
