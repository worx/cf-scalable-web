Great question — you're right to poke at this. Short answer: **yes, our current env-var approach breaks in multi-tenant, and the plan already addresses it, but I should walk you through the mechanism because it's non-obvious.**

## Why env vars break in multi-tenant

Today:
1. `configure-php.sh` runs at instance boot, reads SSM + Secrets Manager, writes `env[DRUPAL_DB_HOST]`, `env[DRUPAL_DB_NAME]`, `env[DRUPAL_HASH_SALT]`, `env[AWS_S3_BUCKET]`, `env[DRUPAL_SITE_NAME]` into `/etc/php/8.3/fpm/pool.d/www.conf`
2. PHP-FPM master starts, all workers inherit those env vars
3. Every request `getenv()`s the same values

Env vars are **process-level state**. If one PHP-FPM `[www]` pool serves both Site A and Site B, they physically cannot see different `DRUPAL_DB_HOST` values — the process has ONE, set at boot.

## What the plan does about it (Phase 2)

Phase 2 strips per-site env vars OUT of the FPM pool. After Phase 2 the FPM pool env[] block contains ONLY truly cross-site infra:
- `ENVIRONMENT_NAME` (sandbox/staging/prod)
- Valkey endpoint + auth token

Per-site data (DB creds, salt, S3 bucket, site name) moves OUT of PHP-FPM env vars and INTO a per-site file: `/etc/worxco/sites/<env>/<site>.env`.

## How it works at request time

1. Browser → ALB → nginx → NLB → PHP-FPM pool → worker
2. Nginx routes on Host header → matches `zoning_info_platform.conf` vhost → sets `root /var/www/zoning_info_platform/web` and `fastcgi_pass php83`
3. Worker gets `SCRIPT_FILENAME=/var/www/zoning_info_platform/web/index.php`
4. Drupal boots → loads `/var/www/zoning_info_platform/web/sites/default/settings.php`
5. **That settings.php uses `__DIR__` to know its own location** → reads `/etc/worxco/sites/sandbox/zoning_info_platform.env`
6. settings.php populates `$databases`, `$settings['hash_salt']`, `$settings['flysystem']` directly from the parsed file — no `getenv()` needed

**Key insight**: each site's `settings.php` lives in its OWN directory tree, so it self-identifies via `__DIR__`. Nginx doesn't need to tell PHP-FPM which site it is — the fact that PHP loaded *this* settings.php from *this* path implicitly identifies the site. Zero cross-site leakage.

## What DOESN'T change

- PHP-FPM still uses env vars for shared infra (ENVIRONMENT_NAME, Valkey)
- `configure-php.sh` still runs at boot to inject those
- `refresh-env-config` still writes `/etc/worxco/envs/<env>` (infra-only after Phase 2)
- What's ADDED: per-site env files under `/etc/worxco/sites/<env>/`, populated by a new pass in `refresh-env-config` that walks SSM `/<env>/sites/*/` and writes one file per site

**In one sentence**: env vars stop carrying site-specific state; they only carry shared infra state. Per-site state moves to per-site files that each site's own settings.php reads at request time.
