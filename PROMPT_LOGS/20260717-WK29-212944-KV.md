auxiliary files those scripts depend on. run-pgloader.sh's default

which, in the remote /opt/migration layout, becomes
/opt/migration/pgloader/zinew.load.tmpl — a file that was never
uploaded, so run-pgloader bailed at Phase 1 preconditions.

Direct `make run-pgloader` worked because it runs from the local
checkout where the template exists. Dispatch didn't work because the
uploaded structure only had scripts, not templates.

## Fix

New Step 3b in _ssm-run-deploy-host.sh: script-specific auxiliary
file uploads via a `case "$SCRIPT_NAME"` block. Currently:

  run-pgloader → uploads migration/pgloader/zinew.load.tmpl to
                  s3://<bucket>/scripts/pgloader/zinew.load.tmpl

Then the SSM inner script (built by jq) picks up the file with an
extra download step:

    mkdir -p /opt/migration/pgloader
    aws s3 cp s3://.../scripts/pgloader/zinew.load.tmpl \
              /opt/migration/pgloader/zinew.load.tmpl --quiet

The extra-download step is threaded through jq via a new `--arg extra`
that expands to the mkdir+cp shell fragment for run-pgloader, and to
`true` (a shell no-op) for scripts with no extras — keeps the JSON
structure valid without a conditional at the command-array level.

## Extending for future

If we add more remote scripts with companion files, add cases to the
same block. E.g., if run-pgloader ever picks up multiple templates:

    run-pgloader)
      aws s3 cp pgloader/zinew.load.tmpl s3://.../scripts/pgloader/
      aws s3 cp pgloader/OTHER.load.tmpl s3://.../scripts/pgloader/
      EXTRA_DOWNLOAD_CMDS='mkdir -p /opt/migration/pgloader && ...&& ...'
      ;;
