## Cloud-init status vs functional health

Worth separating two things:

- **cloud-init reports `error`** = one of its modules exited non-zero. Some downstream tools (like our `make wait-deploy-host-ready`) treat this as "boot failed."
- **Functional health** = does the box actually work? SSH keys landed, drupal deploys, etc.

These often disagree — especially with `set -euxo pipefail` in UserData where one strict-mode failure marks the whole boot as errored even if the important parts succeeded.

## What I'll do based on your findings

Paste back the output from those 6 checks and I can pin the root cause:

- **If credentials stub exists AND files restored:** the failure was in Phase 6/7 (post-restore verify/announce). Restore was 90% successful. Small fix needed for robustness.
- **If files restored but stub missing:** Phase 5 crashed. Something wrong with the `install` command or file permissions.
- **If NO files restored:** restore-state.sh failed early (Phase 1-3). Might be a permission/network issue at boot time.
- **If UserData never called restore-state.sh:** the failure is in our UserData block itself (mkdir, aws s3 cp, or chmod). Least likely given the log shows the s3 cp succeeded.

Once we know which phase died, the fix is targeted.
