## Now your question about `drupal-private.BAK.20260718-031235Z`

Great question — that's exactly the class of "safety-net leftover" that accumulates over time and eventually eats FSx space.

## What those BAK dirs are

Every `restore-*` script (`restore-files`, `restore-private`, `restore-codebase`, and now the multi-top-level swaps within restore-codebase) does an **atomic swap**:
1. Rename existing dir to `<name>.BAK.<STAMP>`
2. Move `<name>.NEW.<STAMP>` into place as the new dir

With `KEEP_BAK=yes` (the default), the `.BAK.<STAMP>` dir stays forever until manually deleted. That's intentional — it's the rollback safety net if the restore turned out to be bad. But once you've verified the restore works, keeping it is pure disk waste.

## Safe to delete?

**Yes**, if you don't need the pre-restore state anymore. That specific `drupal-private.BAK.20260718-031235Z` is from a `restore-private` run on 2026-07-18, 11 days ago — you've been running the migrated Drupal successfully since then, so the pre-migration private state isn't rescuing anyone.

## How to see what's accumulated

```bash
# On deploy-host (or any FSx-mounted host):
sudo du -sh /var/www/*.BAK.* /var/www/drupal/*.BAK.* 2>/dev/null | sort -h
```

Any `*.BAK.<STAMP>` dirs from `restore-files`, `restore-private`, `restore-codebase`, or `install-drupal` are the same class — old safety nets.

## Nuclear one-liner if you're comfortable

```bash
sudo rm -rf /var/www/*.BAK.* /var/www/*.RESTORE-STAGING.*
```

## Two possible follow-up improvements

Not urgent, but worth flagging for future work:

1. **`make clean-migration-baks`** — a Makefile target that lists `*.BAK.*` and `*.RESTORE-STAGING.*` dirs across all FSx-mounted paths with sizes, then optionally deletes them (with `CONFIRMED=yes` gate).
2. **Auto-prune after N days on next restore** — restore-codebase.sh could delete `*.BAK.*` dirs older than 30 days (or whatever) at the start of its run. Automates the cleanup without operator intervention.

If you want either of these, say the word — small work. Otherwise leave `.BAK` management as an ops task.
