### 11:37:28 - Response

Real environment gap: after destroy-all → deploy-all, `/etc/worxco/envs/sandbox` on the deploy-host still has stale content (or missing `DRUPAL_DB_HOST` — the new RDS endpoint). The error message tells you exactly what to do:

> `Rebuild env file: sudo refresh-env-config sandbox`

`refresh-env-config` re-queries SSM for the current values (DRUPAL_DB_HOST, DRUPAL_DB_PASS, hash-salt, AWS_S3_BUCKET, etc.) and rewrites the env file. Fresh CFN stacks → new SSM values → env file needs to be regenerated.

## Recovery for THIS run

```bash
# On deploy-host:
sudo refresh-env-config sandbox

# Verify it has DRUPAL_DB_HOST now:
grep DRUPAL_DB_HOST /etc/worxco/envs/sandbox
# expected: export DRUPAL_DB_HOST=sandbox-postgres.<hash>.us-east-1.rds.amazonaws.com

# Then continue migration, skipping the already-done phases:
cd migration
make migrate-full-all SKIP_PREFLIGHT=yes SKIP_BACKUP=yes
```

- `SKIP_PREFLIGHT=yes` — skip Phase -1 (install-drupal already ran successfully)
- `SKIP_BACKUP=yes` — skip Phase 0 (fresh install; nothing worth backing up)

Then Phase 1 (restore-mysql) picks up where it left off — pulls the ~2.4GB dump from S3 again (fast, ~30 sec), loads it into local MariaDB, and Phase 2 (pgloader) will have `DRUPAL_DB_HOST` this time.

## Why this happened — worth adding to Phase D backlog

`refresh-env-config` isn't auto-invoked anywhere in the deploy-all → migrate-full-all chain. It's assumed to be a manual step the operator runs after any infra changes to the RDS endpoint, media bucket, etc.

For a **fresh destroy-all → deploy-all**, the env file is guaranteed stale. It should be regenerated automatically at some point. Best fit is probably a Phase -2 in `migrate-db-all` that just runs `sudo refresh-env-config $(ENV)` — makes migration always run against current SSM state.
