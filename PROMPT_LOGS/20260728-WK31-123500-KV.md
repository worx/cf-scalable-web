Both "failures" are the same underlying issue — `sudo -u www-data php -r` is a **CLI** invocation, not a PHP-FPM worker. `env[…]` directives in `www.conf` only reach **PHP-FPM worker processes**, not CLI processes started by other means. So `getenv('AWS_S3_BUCKET')` returns `false` in your test even though FPM workers themselves absolutely see it. The second failure chains from the first — `Bucket => false` gave the validator crash.

**Fresh instance → FPM master started with the new pool.d config → workers already have env[AWS_S3_BUCKET] baked in.** No restart needed.

## Better verification — check an actual FPM worker's environ

```bash
# Find any FPM worker (not the master):
FPM_PID=$(pgrep -f 'php-fpm: pool www' | head -1)
echo "Worker PID: $FPM_PID"

# Read its actual environ from /proc — this is the truth about what the
# worker was launched with:
sudo cat /proc/$FPM_PID/environ | tr '\0' '\n' | grep -E 'AWS|ENVIRONMENT|DRUPAL_DB'
```

Expected: you see `AWS_S3_BUCKET=sandbox-drupal-media-kv-worxco` along with the other env[] vars (DRUPAL_DB_HOST, DRUPAL_HASH_SALT, etc.).

