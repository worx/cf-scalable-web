Not confused — there's a coherent explanation for the size difference. Let me walk through what's likely happening:

## Why `drupal.BAK` is 4.6x larger than fresh `drupal`

Fresh `/var/www/drupal` (from the tarball) contains **only what dump-codebase captured on React2** at dump time — no accumulated runtime state. The `.BAK` contains **everything sandbox had built up** over its whole lifetime. Rough breakdown of the extra ~3.8 GB:

1. **`web/sites/default/files/`** — the biggest one, almost certainly. Even though we're storing user media in S3 now via flysystem, Drupal still uses this local dir for:
   - CSS/JS aggregation output (`css/`, `js/` subdirs — often 100-500 MB on an active site)
   - **Image styles / thumbnails** — every image displayed at any derived size gets a rendered thumbnail cached here. Prod-migrated content with lots of images = potentially GBs of thumbnails.
   - Twig/PHP compiled cache spillover
   
   dump-codebase explicitly excludes `web/sites/default/files/` (see DRUPAL_EXCLUDES), so it's absent in the new tarball. Present in the BAK.

2. **`vendor/`** — sandbox's had prod's dependencies PLUS my `composer install --no-dev` from last night that got restored WITH dev packages later. Prod's tarballed vendor is smaller (no test packages, no dev tools). Probably a few hundred MB delta.

3. **`.git`** — dump-codebase globally excludes `.git`, but the SANDBOX's `/var/www/drupal/.git` (from `install-drupal.sh`'s composer setup, or from Kurt's manual tarball extraction last night) is IN the BAK. Could be 100-500 MB depending on history depth.

4. **Runtime-generated stuff** — Twig cache, container cache, service.yml, private tmp, `sites/default/files/private_stuff`, etc.

The same explanation applies to the sibling BAKs — Kurt's manual tarball extraction last night likely didn't exclude `.git`, so `entity_bundle_manager.BAK` has that module's git history (200KB) while the new one (from our tarball with `.git` excluded) doesn't (55KB).
