## Your two proposals — validated

**1. Background `destroy-migrate-host` (Phase 4).**
- Depends on: Phase 3 complete
- Downstream deps: NONE in Phases 5-11
- Save: ~3 min off critical path
- Effort: trivial (change `make destroy-migrate-host CONFIRMED=yes` to `make destroy-migrate-host CONFIRMED=yes &` and add a `wait` at end of script)
- Caveat: if destroy fails silently in background, you won't notice until next run's SSM/CFN state shows an orphan. Mitigation: check exit code at final wait.

**2. Move file/media restores to migrate-host with FSx.**
- Real trade-off. Correct instinct on the network cap: **t4g.small has 5 Gbps burst / 32 MB/s baseline** (yes, MEGABYTES not gigabits — the AWS UI's "underperforming at network I/O" note is telling you this). **r7g.xlarge has up to 12.5 Gbps sustained**. Roughly **~40x more sustained bandwidth**.
- With that headroom, restore-codebase + restore-files + restore-private could run truly concurrent instead of bandwidth-bound serial.
- Save: probably 10-15 min (concurrent + faster download)
- Effort: **moderate-to-large** — requires:
  1. FSx mount in migrate-host bootstrap.sh (5-10 lines)
  2. FSx security group ingress from migrate-host subnet (CFN edit)
  3. Extend migrate-host lifetime past DB migration into file-restore window (change destroy timing to Phase 8+)
  4. Route restore-* dispatches to migrate-host (HOST_STACK variable propagation, similar to bug #2 in reverse)

## Additional parallelization I see

**3. Pre-warm sync-s3-media during deploy-all.** ⭐ Biggest untapped win.
