feat(deploy-host): inject-flysystem-config.sh — safe settings.php surgery

Bridges the gap between install-drupal.sh's *template* (which writes
the flysystem block on FRESH installs only, via `drush site:install`
which is destructive) and *running* Drupal installs that were done
before the flysystem commit landed. Appends the same flysystem_s3
block to an existing settings.php without re-running the installer,
without dropping the DB, and without hand-editing.

## Why this exists

install-drupal.sh commit 4959433 added the flysystem_s3 block to the
settings.php TEMPLATE. That works for future installs. But the
sandbox is already installed and serving pages. Re-running
install-drupal.sh would call `drush site:install`, which drops all
Drupal tables and recreates them — blowing away whatever's in the
sandbox DB. Not acceptable for a running install we want to keep.

Options considered:
  a. Hand-edit — brittle, easy to typo, no idempotency guarantee
     across envs (sandbox → staging → prod, if we ever do this
     three times).
  b. Extend install-drupal.sh with an `--append-flysystem-only`
     flag — dilutes the semantics of that script (which is "install
     Drupal from scratch"). Prefer a dedicated tool.
  c. This script — a one-off surgeon for a very specific edit.

## Safety envelope

1. `grep` for BEGIN marker → if present, no-op with OK message
   (idempotent — re-run costs nothing, produces same state)
2. `php -l` on the file BEFORE edit — refuses to touch a
   pre-broken settings.php (defensive; would surface an existing
   syntax problem to the operator instead of masking it)
3. Timestamped backup (.pre-flysystem-YYYYMMDD-HHMMSS) — rollback is
   one `cp` command
4. Append the block with BEGIN/END markers
5. `php -l` AGAIN — if the post-edit file is broken (e.g., an
   unbalanced brace in a hand-tweaked settings.php we ran into
   mid-block), auto-restore from backup and exit non-zero

## Idempotency marker

The block is delimited by:
  // BEGIN worxco-flysystem-s3 (managed by inject-flysystem-config.sh — do not edit)
  ...
  // END worxco-flysystem-s3

Marker-based idempotency matches the pattern used by
refresh-env-config for the /etc/hosts FSx block. Same predictability.

## Delivery — not a /usr/local/sbin/ install

install-drupal.sh, use-env, refresh-env-config live in
/usr/local/sbin/ because they're invoked often. This one is a
one-per-env-per-lifetime operation (bring an existing install up to
the current settings.php template). Run it directly from the git
checkout:

  sudo bash /home/ubuntu/projects/cf-scalable-web/scripts/deploy-host/inject-flysystem-config.sh

No sudoers rule needed — full sudo. No bootstrap.sh change.

## Usage

  sudo bash scripts/deploy-host/inject-flysystem-config.sh
  # → operates on /var/www/drupal/web/sites/default/settings.php by default

  sudo bash scripts/deploy-host/inject-flysystem-config.sh /custom/path/settings.php
  # → operates on the given file

## Rollback

  cp settings.php.pre-flysystem-YYYYMMDD-HHMMSS settings.php

## What this script does NOT do

- Does not update /etc/worxco/envs/<env> — that's refresh-env-config's job
- Does not touch PHP-FPM pool config — configure-php.sh's job (runs at boot)
- Does not restart php-fpm — operator responsibility (nothing to restart
  yet on deploy-host; on compute instances, ASG cycle or SSM one-off)
- Does not composer-install flysystem_s3 module — operator responsibility
  (verify with `composer show | grep flysystem` before running)
