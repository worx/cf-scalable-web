feat(deploy-host): refresh-deploy-host-scripts — reinstall /usr/local/sbin/ copies without full bootstrap

bootstrap.sh installs three helpers as COPIES (not symlinks), so
`git pull` on the deploy-host updates the checkout but leaves the
installed versions stale until the next full bootstrap:

    /usr/local/sbin/use-env
    /usr/local/sbin/refresh-env-config
    /etc/sudoers.d/worxco-refresh-env-config

Discovered live 2026-07-20 during the salt→SSM upgrade path. Kurt
git-pulled the updated refresh-env-config, ran it, and got no
DRUPAL_HASH_SALT line in the env file — because the installed copy
at /usr/local/sbin/ was still the pre-commit version. Only fix was
manually running the three `install` commands from bootstrap.sh:519-521.

## What this commit adds

`scripts/refresh-deploy-host-scripts.sh` (dispatched from Mac via SSM,
mirrors the clear-drupal-cache.sh inline-base64 pattern):

- Runs `git pull` on the deploy-host's checkout (best-effort; falls
  through to reinstalling from existing checkout if pull fails)
- Reinstalls the three helpers with the exact modes bootstrap.sh uses
  (`install -m 0755` for the scripts, `install -m 0440` for the sudoers)
- Prints ls of the installed files for verification

`make refresh-deploy-host-scripts` — Mac-side wrapper.

## When to reach for it

- After `git pull` on the deploy-host that touched any of
  `use-env`, `refresh-env-config`, or the sudoers file
- Anytime you notice a helper is behaving like the pre-commit version
  (like today's DRUPAL_HASH_SALT case)
- Faster than re-running the full bootstrap (~5 seconds vs ~10 minutes)
