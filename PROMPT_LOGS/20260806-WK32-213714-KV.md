That's ~2.5x over the design-doc target (8-12 min). And the "threads at rest more than working" is basically confirming my earlier suspicion: pgloader isn't compute-bound on the migrate-host — **RDS is the throttle.**

Which means Phase 2's compute-side tuning (buffer pool, worker count, concurrency, batch size, heap) didn't move the needle much because the bottleneck was never on our side. The migrate-host's 4 cores + 32 GB are overkill relative to what RDS can consume per second.

**Don't kill it — let it complete.** We need three data points from the finished run:

1. **Total wall time.** Even if it's 45 min, that's a real number vs the deploy-host baseline (~30 min per Makefile comments). If migrate-host = deploy-host = both bottlenecked on RDS, then Phase 2 saved us nothing on pgloader specifically. That's valuable to know before Phase 5.

2. **Per-table timings** (from the S3 log). If a small number of huge tables dominate wall time, concurrency=4 doesn't help — you can't parallelize a single table's load. If wall time is roughly even across all 413 tables, concurrency is working but RDS commit-latency is capping throughput.

3. **RDS-side metrics during the run.** Once done, we can pull CloudWatch: `WriteIOPS`, `WriteLatency`, `WriteThroughput`, `CPUUtilization`, `DiskQueueDepth`. If IOPS is pinned at the RDS instance class limit, we've found the ceiling.

**What this means for the plan long-term:**
- **restore-mysql win is real** (3:16 vs 10-15 min baseline). Phase 2's MariaDB tuning delivered.
- **pgloader win may be marginal.** If confirmed, real speed wins for pgloader require upgrading RDS instance class (more IOPS + faster commit) or temporarily disabling `synchronous_commit` on RDS during migration — both are RDS-side changes, not migrate-host changes.
- **Doesn't invalidate the migrate-host architecture** — moving MariaDB off deploy-host is still the right call for isolation, ephemeral cost, and future-proofing.

Just let it cook. Send me total wall-time when it lands and I'll pull the S3 log.
