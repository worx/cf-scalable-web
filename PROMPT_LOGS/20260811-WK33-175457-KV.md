Interesting — DNS ruled out. So the request IS reaching the correct ALB, and one client (curl) gets 200 while another (browser) gets 500. That's a real puzzle.

Two most likely causes, both testable:

**Theory A: Drupal's "generic error" masks the real exception.** The "encountered an unexpected error" message is Drupal's production-mode fallback for uncaught exceptions. The real exception is in the `watchdog` table. Curl might be seeing a cache-primed 200 for `/` while the browser hits an error-triggering downstream page.

**Theory B: The 200 response has an HTML meta-refresh pointing at a broken URL.** Curl returns 200 (which smoke-test happily accepts); browser follows the meta-refresh and lands on a 500. Similar to the pre-migration `/core/install.php` redirect but pointing somewhere else now.

**Two diagnostics** (do B first — it's from your Mac, 10 seconds):

```bash
# From Mac — dump the raw response body to disk, look for the tell
curl -sL https://sandbox.envs.zoning-info.com/ -o /tmp/resp.html \
  && wc -l /tmp/resp.html \
  && grep -iE "meta.*refresh|http-equiv|error|exception" /tmp/resp.html | head -20
```

If we see a `<meta http-equiv="refresh"...>` line pointing at a URL, that's the smoking gun for Theory B.

If not, or if the response IS itself the error page (not a redirect target), pull the actual Drupal exception from watchdog:

```bash
# On deploy-host — pulls the last 5 Drupal errors with full detail
make ssm-deploy-host
psql-env sandbox <<'SQL'
SET search_path = zinew;
SELECT wid, type, severity, message, LEFT(variables::text, 800) AS vars
FROM watchdog
ORDER BY wid DESC
LIMIT 5;
SQL
```

That will show the actual exception Drupal is throwing — usually a class-not-found, config-missing, or DB-column-mismatch error. Post whatever comes back and I'll parse it.

**Bonus quick check for Theory B: try incognito.** If a fresh session (no cookies from earlier install attempts) works, then a stale session cookie is the smoking gun. Cheapest test of all.
