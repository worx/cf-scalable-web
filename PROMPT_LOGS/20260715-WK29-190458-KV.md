fix(deploy-host): harden UserData auto-restore + add missing operator packages

Two independent findings from the first deploy-host instance replacement
after enabling backup/restore automation:

## 1. UserData auto-restore silently died on missing S3 object

On a fresh deploy-host, UserData tries to fetch _common.sh + restore-state.sh
from S3, chmod, and invoke. Failure mode observed:

  + aws s3 cp .../restore-state.sh --quiet  <-- exited non-zero (object 404)
  (no + chmod trace)
  (no + restore-state.sh trace)

restore-state.sh is only uploaded to S3 when `make restore-deploy-host` runs.
An operator who has only ever run `make backup-deploy-host` has _common.sh
and backup-state.sh in the bucket, but no restore-state.sh. The head-object
check on the tarball succeeds, then aws s3 cp for restore-state.sh returns
non-zero, `set -e` kills UserData BEFORE chmod, and cloud-init reports
scripts_user as failed. `make wait-deploy-host-ready` propagates the failure
even though the instance is otherwise healthy.

Fix: each fallible step now has an explicit `|| { echo REASON; RESTORE_READY=0; }`
guard. --quiet is dropped from aws s3 cp so real error text lands in the log.
A missing restore-state.sh now emits an actionable WARN pointing the operator
to `make restore-deploy-host` (which uploads it as a side effect).

## 2. Operator packages installed during migration were never persisted

Audit of PROMPT_LOGS from the last ~45 days surfaced packages installed
ad-hoc on the deploy-host during the pgloader migration and daily operations
that were never added to bootstrap.sh. On instance replacement they were
lost:

  - mariadb-client  - MySQL/MariaDB CLI (added to Drupal management group)
  - htop            - operator process viewer (we already back up ~/.config/htop
                      but never installed htop itself - the backup is useless
                      without the binary)
  - mlocate         - locate/updatedb (operator diagnostics)
  - pv              - pipeline progress meter (used by mysqldump|ssh|s3 flows)

updatedb runs at end of Core CLI step so `locate` is usable on first boot
instead of waiting for cron.daily.

## Explicitly NOT re-added

- mysql-server / mariadb-server: purged during migration cleanup, project
  moved to RDS - no reason to reinstall a local server on deploy-host
- mysql-client-core-8.0: mariadb-client is the modern drop-in
- php8.2-cli / php-cli: superseded by php8.3-cli (already installed)

## Verification

- bash -n /scripts/deploy-host/bootstrap.sh: clean
- cfn-lint cloudformation/cf-deploy-host.yaml: clean
- Failure mode traced via `sudo grep '^+' /var/log/deploy-host-bootstrap.log`
  on the current running instance (2026-07-15 boot)
- S3 bucket audit confirmed missing object:
    scripts/_common.sh                     PRESENT
    scripts/deploy-host/backup-state.sh    PRESENT
    scripts/deploy-host/restore-state.sh   MISSING <-- root cause

## Follow-up (not in this commit)

  Mac to (a) restore current instance's operator state, (b) upload
  restore-state.sh to S3 as a side effect so future instance replacements
  auto-restore cleanly.
