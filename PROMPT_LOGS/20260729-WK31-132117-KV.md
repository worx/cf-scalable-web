feat(migration): `make clean-migration-baks` — prune restore leftovers

New Makefile target for cleaning the accumulated safety-backup dirs that
migration restore scripts leave on FSx. Each `restore-*` operation does
an atomic-swap that renames the current dir to `<name>.BAK.<STAMP>` and
promotes a new copy from S3. With `KEEP_BAK=yes` (the default), those
`.BAK` dirs stay forever — great for one-restore rollback, but they
accumulate and eat FSx capacity.

Example: sandbox as of 2026-07-29 had drupal.BAK.20260729_135014Z at
4.79 GB alongside a fresh drupal at 1.02 GB — the BAK carried runtime-
generated state (aggregated CSS/JS, image-style thumbnails, .git,
dev vendor packages) that the fresh tarball didn't have.

## Scope of what's cleaned

Under `/var/www/`:
- `*.BAK.<STAMP>`            — safety backups from restore ops
- `*.NEW.<STAMP>`            — mid-swap detritus from aborted restores
- `.RESTORE-STAGING.<STAMP>` — extract-staging detritus from aborted
                                restore-codebase runs

Never touches `/var/www/drupal` itself, or the sibling composer packages
(`entity_bundle_manager`, `filtered_entity_reference`) at their live
paths — only their `.BAK.<STAMP>` siblings.

## Universal entry point — one command works everywhere

The dispatcher auto-detects the environment and routes accordingly:

  From Mac (Darwin):            SSMs to deploy-host, runs worker there
  On deploy-host as ubuntu:     `sudo bash …` the worker directly
  On deploy-host as root:       `bash …` the worker directly (no sudo)
  Anywhere else:                error out with a clear message

Detection heuristic for deploy-host: `/etc/worxco` exists AND `/var/www`
is an NFS mount. Doesn't rely on hostname patterns (which would break
with ASG rotation).

## Behavior of the worker itself

- Without `CONFIRMED=yes`: dry-run listing. Each candidate shown with
  human-readable size and age. Grand-total size printed. No deletion.
- With `CONFIRMED=yes`: `rm -rf` each candidate, reports what got cleaned.
- Refuses to run as non-root (the dispatcher handles the sudo).
- Zero candidates → prints "Nothing to clean" and exits 0.

## Invocation (always the same)

  make clean-migration-baks               # dry-run
  make clean-migration-baks CONFIRMED=yes # actually delete

## Files Created / Modified

- migration/scripts/deploy-host/clean-migration-baks.sh (new)
    The worker. Lives alongside other migration workers
    (restore-codebase.sh, restore-mysql.sh, run-pgloader.sh) in
    migration/scripts/deploy-host/ — since it's cleaning up MIGRATION
    residue, that's the right neighborhood, not the general
    scripts/deploy-host/.
- scripts/dispatch-clean-migration-baks.sh (new)
    Universal entry point. Detects Darwin vs Linux, sudo-vs-not, and
    routes.
- Makefile — new `clean-migration-baks` target near
  refresh-deploy-host-scripts.

## Not in scope (deliberate)

- `/var/www/mysql/*` — MariaDB scratch area kept between migration
  cycles. Operator wipes manually when done.
- Age-based auto-prune — every BAK is an operator's explicit safety
  net; auto-deleting them behind the operator's back is a bad default.

Tests: bash -n clean on both scripts. Grep for stale
`scripts/deploy-host/clean-migration-baks` (pre-move) references — none
found.
