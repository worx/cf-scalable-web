## What that means for the migrate-host-for-files bet

**Corrected root cause reasoning for the 17 min:**
- Download 716 MB from S3 at ~32 MB/s = ~22 sec (fast — S3 endpoint is nearby)
- **Extract 716 MB / 80K files to FSx** = ~16 min (the actual bottleneck)

The extract writes 80K small files to FSx. FSx metadata operations (create-file, set-permissions, etc.) are bounded by FSx's IOPS provisioning, NOT by the client's CPU or network. **If FSx metadata is the ceiling, moving the client to migrate-host doesn't help.**

Three possible profiles for the 16-min extract time:
1. **CPU-bound** (tar decompression): migrate-host wins big. But 716 MB gzip decompress is ~10-20 sec on any modern CPU, so unlikely.
2. **Network-to-FSx-bound** (NFS write): migrate-host's better network could help. But NFS write speed to FSx is generally bounded by FSx, not client.
3. **FSx-metadata-bound** (80K file-create ops): migrate-host doesn't help. Only FSx tier upgrade or fewer files would.

**Most likely: mostly #3, some #2.** Migrate-host bet would probably save 3-6 min, not 15-20 min.
