### 10:17:51 - Response

Great catch, and yes — you've identified a real design coupling.

## Direct answer

**install-drupal.sh IS required before migration.** For a fresh sandbox → prod-data pipeline, the sequence is:

1. Deploy infra (VPC, RDS, FSx, deploy-host, compute) via top-level Makefile
2. Run `make install-drupal ENV=sandbox` — bootstraps Drupal on sandbox
3. Run `make migrate-full-all` — replaces DB + files with prod's

## What migration ASSUMES exists before it runs

Migration is a "swap the contents" operation. It relies on install-drupal having produced:

| Thing | Where | Why migration needs it |
|-------|-------|-----------------------|
| Drupal codebase on FSx | `/var/www/drupal/web/`, `/vendor/` | Drupal wouldn't boot even with data; run-pgloader still works but the site couldn't serve |
| `settings.php` | `/var/www/drupal/web/sites/default/` | Env-var-driven DB/cache/host config. Migration doesn't touch it. |
| `drupal` Postgres DB | RDS | Phase 0's `db-backup` renames an EXISTING drupal DB. Nothing to rename if it doesn't exist. |
| `drupal_user` role in Postgres | RDS | Migration creates the fresh drupal DB owned by `drupal_user`. Role must exist. |
| Secrets in Secrets Manager | `worxco/sandbox/drupal/db-password`, admin-password | drupal_user's password. settings.php reads it. |
| `salt.txt` on FSx | `/var/www/drupal-private/salt.txt` | The one we just discussed. |
| `.installed` marker | (soon-to-be-optional per the structural-check refactor) | Currently used by some scripts; being replaced |

install-drupal.sh creates all seven. Migration builds ON that foundation.

## Options to make this less brittle

**Option A: Precondition check in migrate-full-all** (small, targeted, do this)

Before Phase 0, verify sandbox has Drupal installed. Use the structural check pattern we already established:

```bash
# Pseudo — a new Phase -1
[ -x /var/www/drupal/vendor/bin/drush ] \
  && [ -f /var/www/drupal/web/sites/default/settings.php ] \
  && [ -f /var/www/drupal-private/salt.txt ] \
  || fail "Drupal not installed on sandbox. Run: make install-drupal ENV=sandbox first."
```

Fail fast with a clear message rather than blowing up mid-Phase-2 with a mysterious hash_salt error. **Small commit, high value.**

**Option B: Move salt.txt to SSM SecureString** (bigger, cleaner, do it eventually)

Per `docs/memory/salt-persistence-design.md`, this is the aspirational fix. Salt lives at `worxco/${ENV}/drupal/hash-salt` in Secrets Manager alongside the DB password and admin password. `refresh-env-config` fetches and exports as `DRUPAL_HASH_SALT`. `settings.php` reads from `getenv('DRUPAL_HASH_SALT')` instead of file. `install-drupal.sh` generates + writes to SSM.

Then:
- No dependence on file existence in `/var/www/drupal-private/`
- `restore-private` doesn't need the preserve list (salt isn't in the target dir at all)
- Cross-env independence is enforced by IAM (each env's role has access to only its own secrets)
- Consistent with all other Drupal secrets

**Option C: Make migration flow auto-invoke install-drupal if missing** (probably wrong)

Have `migrate-full-all` detect an unbootstrapped sandbox and run install-drupal first. Feels tempting but it makes migration do too much — better to keep migration as "swap contents" and let install-drupal be a separately-invoked bootstrap step. Compose in the operator layer, not the tool layer.

## My recommendation

Now: **Option A**. Small commit. Precondition check on `migrate-full-all` (and probably the individual `dispatch-*` targets too). Prevents the exact class of surprise you hit — "why did Phase 2/3 fail" when the real answer is "install-drupal was never run."

Later (queue as follow-up): **Option B**. Salt-to-SSM. Cleaner architecture, no more preserve-list needed, matches how other secrets are managed.
