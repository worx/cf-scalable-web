Pushed (`cd2d55b`). Now let's investigate the `wait-deploy-host-ready` failure.

## Reading the pattern

**The bottom-line observation matters most:** you SSM'd in and confirmed the auto-restore worked, your files are there. So the deploy-host is functionally healthy.

**The `wait` failure is about cloud-init reporting a non-zero exit somewhere in UserData** — even though functionally it landed fine. The `wait-deploy-host-ready` target invokes `cloud-init status --wait` on the instance via SSM, and if cloud-init sees any module failure (even one that didn't affect the boot), it returns failed.

## Investigate — three quick checks

SSM into the deploy-host and run these:

```bash
make ssm-deploy-host
```

Once inside:

```bash
# 1. What does cloud-init itself say went wrong?
sudo cloud-init status --long

# 2. Look for the specific "failed" step
sudo grep -iE 'fail|error' /var/log/cloud-init.log | tail -30

# 3. Confirm the auto-restore section succeeded despite whatever failed
sudo grep -B 2 -A 20 "deploy-host state" /var/log/cloud-init-output.log
```

## My prime suspects (in order of likelihood)

**1. bootstrap.sh had a non-fatal error** that predates our auto-restore changes. Could be:
- A `set -e` inside bootstrap.sh triggered on something benign
- An `apt-get install` warning that returned non-zero
- A conditional check (like `git clone` when repo already exists after auto-restore populated /home/ubuntu/projects)

Given auto-restore runs AFTER bootstrap.sh, this seems unlikely to be caused by our changes.

**2. Auto-restore itself exited non-zero, and the `|| echo` didn't fully suppress it.** Unlikely because `command || fallback` should mask the exit code, but worth verifying by looking at the actual UserData output.

**3. Some cloud-init module unrelated to our UserData**. cloud-init runs multiple modules (network config, user setup, etc.). Any one failing marks status as `failed` even if your UserData scripts completed fine.

## What I'd bet on

Looking at the timing: **1m32s at Stage 2** is very fast for a fresh deploy-host. bootstrap.sh normally takes several minutes to install packages, clone repo, etc. That suggests cloud-init reported failed EARLY — possibly on a module that ran before your UserData even fired.

If option 3 is right (an unrelated cloud-init module failed), the wait check is being overly strict. That's a Makefile improvement to consider — check for actual UserData success rather than global cloud-init status.

But diagnose first. Paste back the output from `sudo cloud-init status --long`, that'll pin it down definitively.
