### 14:44:11 - Response

Good architectural question. Looked at what's IN `cf-app-drupal.yaml`:

- **2 Secrets Manager entries** — DrupalAdminPasswordSecret + DrupalDBPasswordSecret (both generated on stack CREATE, then stable)
- **6 SSM parameters** — DB name, DB user, site name, install path, admin username, admin email (all constants)

Notably NOT there:
- Hash salt (that's created by `install-drupal.sh` at install time, lives at `worxco/${ENV}/drupal/hash-salt` — separate secret, not owned by this stack)
- RDS endpoint (that's cf-database's territory)
- Media bucket name (that's cf-storage-s3's territory)

## My read — it's probably INTENTIONAL that it survives destroy-all

Here's why:

1. **Password stability across cost-cycling.** When you `pause-compute` / `resume-compute` or fully destroy → redeploy, the admin password + DB password stay the same. You don't have to look up new credentials each cycle. Predictable identity per environment.

2. **What actually happens on rebuild:** `make deploy-app-drupal` runs → CFN sees no drift → no-op → done in seconds. Then `install-drupal.sh` reads the SAME DrupalDBPasswordSecret → creates the drupal_user DB user with the SAME password → Drupal has continuity.

3. **Cost is nothing** — 2 secrets × $0.40/mo = $0.80/month.

## But there's a lifecycle question worth thinking about

The **hash salt secret** (`worxco/${ENV}/drupal/hash-salt`) survives too — but it's created dynamically by `install-drupal.sh`, NOT by this stack. It's an implicit "orphan" resource — no CFN stack owns it. When you destroy-all, the salt secret remains. When `install-drupal.sh` runs fresh, it reuses the existing salt (per `docs/memory/salt-persistence-design.md`). That's by design so user sessions/tokens continue to work across compute cycles.

So the WHOLE per-env-secrets ecosystem is designed to be resilient to destroy-all. cf-app-drupal being outside destroy-all is consistent with that.

## Recommendation — three options for Phase D

1. **Leave cf-app-drupal out of `destroy-all` as-is (current behavior)** — document it clearly with a comment in the destroy-all-parallel TRACKS section explaining why. Also document the hash-salt-secret-survives-destroy-all invariant.

2. **Add a `destroy-app-drupal` Makefile target** — explicit, one-off, Kurt-invoked only when doing a true nuclear rebuild ("also wipe secrets"). Not part of `destroy-all`.

3. **Add a `destroy-all-nuclear` variant** — includes app-drupal + hash-salt secret + anything else designed-to-survive. For "start from scratch, generate all new credentials" scenarios.

**My vote: 1 + 2.** Document the intent clearly, add the explicit escape hatch. Skip #3 (feels like premature machinery — Kurt can just run `make destroy-app-drupal` manually if needed).

## For today's rebuild — no change needed

The current behavior is fine. cf-app-drupal stays, deploy-all's `deploy-app-drupal` will no-op (stack unchanged), and install-drupal.sh will use the existing credentials. Continuity intended.
