### 15:12:36 - Response

Two answers.

## Re: `-U` to psql-env

Technically yes — the hardcoded `-U dbadmin` gets overridden by a later `-U drupal_user` (last one wins in psql). But **two things prevent it from working:**

1. `PGPASSWORD` is fixed to dbadmin's password from Secrets Manager, so `-U drupal_user` fails auth
2. Even if we fixed auth (fetch drupal_user's password separately, use raw `psql`), **drupal_user doesn't have CREATEDB** — it was created via `CREATE USER :"db_user" WITH PASSWORD :'drupal_db_pw'` at `install-drupal.sh:274`, plain vanilla (no CREATEDB, no CREATEROLE). Postgres' `ALTER DATABASE ... RENAME` requires CREATEDB regardless of ownership.

So even connecting as drupal_user, the rename fails.

**Enhancing `psql-env` to accept `-U` and route to the right secret** would be a nice ergonomics win — but doesn't help THIS operation because of the CREATEDB issue.

## Re: persistence

Legitimate concern — you're right that "GRANT drupal_user TO dbadmin" persists at the RDS cluster level and would survive until the next teardown, silently expanding dbadmin's capabilities in the meantime.

**Solution: do the grant AND the revoke inside the same script.** After the block runs, the DB is renamed but role membership is exactly as it was before we started. Pure transient elevation:

```bash
STAMP=$(date -u +%Y%m%d_%H%M%S)
BACKUP_DB="drupal_backup_$STAMP"
echo "Backup DB name will be: $BACKUP_DB"

psql-env sandbox -d postgres <<SQL
-- Transient elevation: dbadmin joins drupal_user role temporarily
GRANT drupal_user TO dbadmin;

-- Take ownership of drupal (dbadmin has CREATEDB; ownership shift needs role membership, now satisfied)
ALTER DATABASE drupal OWNER TO dbadmin;

-- Kick active connections off drupal
REVOKE CONNECT ON DATABASE drupal FROM PUBLIC, drupal_user;
SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname='drupal' AND pid<>pg_backend_pid();

-- Rename current drupal → backup
ALTER DATABASE drupal RENAME TO $BACKUP_DB;

-- Create fresh empty drupal DB (as dbadmin, owned by drupal_user)
CREATE DATABASE drupal OWNER drupal_user;

-- Restore backup DB ownership to drupal_user
ALTER DATABASE $BACKUP_DB OWNER TO drupal_user;

-- Restore CONNECT
GRANT CONNECT ON DATABASE drupal TO drupal_user;
GRANT CONNECT ON DATABASE $BACKUP_DB TO drupal_user;

-- CLEANUP: undo the temporary elevation. Post-run, role graph is exactly as it was pre-run.
REVOKE drupal_user FROM dbadmin;

\l
SQL
```

**Post-run state:**
- `drupal_backup_$STAMP` — owned by drupal_user (as it was originally)
- Fresh empty `drupal` — owned by drupal_user
- `drupal_user` role: no changes to membership
- `dbadmin` role: no changes to membership
- No persistent grant hanging around

Same clean-slate you'd want.

## For the future

If we do this migration dance often, the right tooling investment is a small `make db-backup ENV=… DBNAME=…` target that wraps this whole heredoc as a proper script (with error handling — if any step fails partway through, roll back the elevation before exiting). Already in the follow-ups list from planning. Not urgent for one-off use.
