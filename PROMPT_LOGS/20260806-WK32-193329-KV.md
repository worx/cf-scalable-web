Found the real issue — and I owe you an apology for the wild goose chase on commas.

**`psql-env` connects as `dbadmin` (the RDS master user), not as `drupal_user`.** Look at line 46 of the script:
```bash
PGPASSWORD="$PASS" psql -h "$RDS" -U dbadmin -d drupal "$@"
```

So all your successful `psql-env` calls have been authenticating as **dbadmin**. drupal_user has never been proven to exist in this RDS instance. And the rollback error `role "drupal_user" does not exist` is now definitive proof: **drupal_user isn't in this database.**

PostgreSQL's default RDS `pg_hba.conf` returns `28P01` (invalid password) for BOTH "wrong password" AND "user doesn't exist" — a security hardening to prevent username enumeration. That's why pgloader's error looked like an auth failure when the real issue was a missing user.

**Root cause:** The recent destroy-all/deploy-all cycles created a fresh RDS instance. drupal_user is created by `install-drupal.sh` (via drush site:install), which was never run against this new database. Your `make status` confirms it — no compute stacks, no install-drupal run.

The comma theory was wrong. Sorry — I anchored on the pgloader auth error and never questioned whether `psql-env` actually proved drupal_user existed. Should have read the script first.
