### 21:58:54 - Response

Interesting hypothesis. Let me push back gently — I think there's less cache benefit between runs than intuition suggests.

**What could actually be cached across pgloader runs on deploy-host:**

- **MariaDB buffer pool for the source data** — the main thing that could persist. BUT `restore-mysql` DROP+CREATE+POPULATE the source DB every run, so the buffer pool gets repopulated with fresh data each time. Both deploy-host AND migrate-host start pgloader against a MariaDB that was just freshly loaded by restore-mysql. Same warmth level.
- **OS page cache for `/var/lib/mysql`** — also freshly written by restore-mysql. Same on both.
- **RDS-side state** — RDS is the SAME instance in both cases. No advantage to deploy-host.
- **pgloader binary / SBCL runtime** — no persistent state across invocations.
- **Postgres query plan cache / prepared statements** — reset per connection. Cold on both.

The one honest advantage deploy-host might have: **familiar operator + more shakedown runs** = more knowledge of what "normal" looks like. That's a psychological factor, not a caching one.

**More likely explanations for slow migrate-host:**

1. **The remembered baseline is against different data.** Right now we did **12M rows / 413 tables / 1706 indexes / 2.2 GB**. If prior runs were against a smaller dump (before more zoning docs got added), direct comparison isn't fair. The Makefile comment even hedges: "up to 2 hours for full 12M-row load" — treating 30 min as the LOWER bound, 2h as upper.

2. **RDS is fresh (post-destroy-all).** The most caching-relevant surface is RDS-side, not migrate-host-side. Post destroy-all/deploy-all, this RDS has cold WAL, cold shared_buffers, no autovacuum stats. First real workload runs slower.

3. **Concurrency=4 might contend at RDS.** Four workers hitting the WAL write lock simultaneously can be *slower* than serial in commit-bound workloads. Worth an A/B test someday.

**A cheap test of your caching theory:**

Rerun pgloader against the SAME MariaDB (skip restore-mysql — it's already loaded) without destroying migrate-host:

```bash
time HOST_STACK=cf-migrate-host CONFIRMED=yes make dispatch-run-pgloader
```

If cache is really the story, this second run — with warm MariaDB, warm OS caches, warm RDS shared_buffers, warm ALB TLS session cache — should be dramatically faster. If it takes the same ~50 min, caching isn't the story and RDS is the bottleneck.

Cheap experiment, 50 min of wall clock, no cost beyond the migrate-host running longer. Want to try before we teardown migrate-host?
