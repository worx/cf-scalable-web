### 14:13:31 - Response

That reality-check changes the calculus significantly — apologies for anchoring on your original 500 MB estimate rather than pushing back on it. **9.9 GB / 80,815 files is a genuinely large payload,** and per-file S3 API latency compounds hard at that count.

Rough math on why it's this slow:
- **Bandwidth-bound floor:** 9.9 GB / 32 MB/s sustained on t4g.small = ~5 min of raw transfer if we were 100% efficient
- **Per-file overhead:** 80K files × ~10-20ms of API + latency + write cost = 15-25 min extra
- **Combined actual observed:** ~20-25 min

Moving to migrate-host would attack both:
- **Bandwidth:** r7g.xlarge sustained ~1500 MB/s vs t4g.small's 32 MB/s = ~40x headroom for the bytes portion
- **Concurrency:** 4 vCPUs vs 2 = doubled parallel S3 GETs (aws cli default 10 concurrent, tunable higher on more cores)
- **Realistic estimate on migrate-host:** 3-6 min for the same payload

**Save potential: 15-20 min off Phase 6.** That's now the biggest remaining single-phase optimization by a wide margin.

## Design implications (not implementing tonight — let this test finish)

Four moving pieces:

1. **cf-migrate-host.yaml**: mount FSx (nfs4 mount, ~10 lines in UserData/bootstrap)
2. **cf-storage-fsx.yaml** (or wherever FSx SG lives): security-group ingress from migrate-host subnet → FSx SG on TCP 2049
3. **migration/Makefile**: `dispatch-restore-codebase` (and files/private) already inherit HOST_STACK env from the caller — no code change needed there IF they currently target deploy-host by default
4. **scripts/full-test-cycle.sh**: wrap Phases 6-8 with `HOST_STACK=cf-migrate-host`; move destroy-migrate-host from Phase 4 to POST-Phase-8

The migrate-host lifetime extends from ~15 min today to ~25 min after this change (destroys after Phase 8 instead of Phase 4). Extra ~$0.05 in r7g.xlarge time. Cheap for 15-20 min saved.

## On the "restore-codebase" name

You're right — bundling `sites/default/` (Drupal-managed user uploads) inside a target called "codebase" is semantically muddled. Files under `sites/default/files/` are content that Drupal writes at runtime, not "code." But splitting into two dispatch targets adds complexity for zero real benefit (same source dir, same restore mechanism, same target host). Cosmetic naming issue — noting it as tech debt but not fixing tonight.
