### 13:48:37 - Response

Strong yes on that plan — my recommendation:

**Excluding cache_* data is pure win.** Cache rows are guaranteed stale on arrival (they reference old class names, cache-tag hashes, container IDs from prod's runtime) and Phase 8 `clear-drupal-cache` TRUNCATEs them anyway. So today those bytes are copied over the network, written to disk, imported into MySQL, dumped again by pgloader, imported into Postgres, and then immediately TRUNCATE'd. Free savings.

**Main tradeoff:** `mysqldump --ignore-table=` doesn't accept wildcards, so the dump script needs a small dynamic-enumeration step (one `information_schema` query → list of tables → build `--ignore-table` flags → two-pass mysqldump: full-except-cache, then `--no-data` for cache structure).

**Related candidates worth thinking about at the same time** (transient/throwaway data): `sessions`, `flood`, `semaphore`, `batch`. All small individually but same "data is worthless on arrival" logic. `watchdog` I'd keep — post-migration prod-error triage is genuinely useful in sandbox.

**Concrete measurement** — I can run `awk` over the 2.4 GB dump we already have to sum bytes-per-table across all `cache_*` entries and tell you exactly how much fat the current pipeline is carrying. Want me to?
