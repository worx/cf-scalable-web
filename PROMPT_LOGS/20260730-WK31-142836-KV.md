## Root cause

pgloader (via SBCL and its PostgreSQL driver) needs HOME to be set
to resolve ~/.pgpass. SSM send-command runs as root but doesn't
export HOME by default. Under root+no-HOME, SBCL's `getpwuid(0)`
path fails and pgloader's connection init aborts.

## Fix

`export HOME="${HOME:-/root}"` early in run-pgloader.sh (before
sourcing _common.sh, before any pgloader-related work). Same guard
install-drupal.sh already has at line 37 for composer, added there
for the same class of "SSM ran us with no HOME" problem.

Also added a comment explaining exactly why the guard is there, so
future me/us don't strip it as "dead code."

## Answering your original question about the timeout

**Setting POLL_TIMEOUT to unlimited would be worse, not better.** Look at your log — the ~1 hour that "passed" was entirely spent hung at pgloader's debugger prompt. If we removed the timeout, it would hang forever until someone noticed and killed it manually. The timeout is your friend — it forced the failure to surface.

## Better diagnostics for "stuck vs slow"

Real ways to distinguish "pgloader working" from "pgloader hung," worth adding to the Phase D backlog:

1. **Progress-log tail in the poll loop.** Every N minutes, dispatcher fetches the last 3 lines of pgloader's log via `aws ssm get-command-invocation --query 'StandardOutputContent'` and prints them alongside the dots. If pgloader is chugging, you see log lines advancing. If hung, you see the same debugger prompt for 30+ min.
2. **RDS side-channel check.** In parallel, poll `SELECT count(*) FROM information_schema.tables WHERE table_schema='zinew'` on the sandbox RDS every 5 min. If count is growing → pgloader is loading. If stuck at 0 or same value for 15 min → pgloader is hung.

Both worth adding but not tonight.
