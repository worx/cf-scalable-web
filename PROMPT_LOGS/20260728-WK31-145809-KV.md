fix(iam): grant PHP compute role s3:GetObjectAcl + PutObjectAcl on media bucket

Discovered while debugging why /_flysystem/s3/... URLs 404'd on sandbox
even though the target files existed in the media bucket AND
file_managed rows existed for them AND flysystem_s3's routes were
registered.

## The chain that produced the 404

1. Browser hits /_flysystem/s3/2026-06/reports/.../foo.pdf
2. flysystem.serve route matches, controller loads
3. Controller opens the file via the s3:// stream wrapper
4. Codementality\FlysystemStreamWrapper (line 938) calls
   $client->getObjectAcl(...) to determine per-object visibility
5. AWS returns AccessDenied — the sandbox-php-instance-role has
   s3:GetObject but not s3:GetObjectAcl
6. Stream wrapper triggers a PHP warning
7. Warning trips Drupal's error handler, page-not-found is set
8. User sees "Page not found" with a matching PHP error in watchdog

Watchdog entry read:
  AWS HTTP error: AccessDenied (client): User: ...sandbox-php-instance-role...
  is not authorized to perform: s3:GetObjectAcl on resource:
  "arn:aws:s3:::sandbox-drupal-media-kv-worxco/2026-06/reports/...pdf"
  because no identity-based policy allows the s3:GetObjectAcl action

## The fix

Two actions added to the existing S3Access policy statement that
already covers `${EnvironmentName}-drupal-media-*`:

  s3:GetObjectAcl   — required for read/serve path (visibility check)
  s3:PutObjectAcl   — required for write path (matching write to scheme
                      visibility). Bundling both because the write path
                      will hit this too as soon as Drupal handles a
                      file upload, and re-deploying IAM twice for
                      symmetric actions on the same bucket is wasteful.

Scoped to the same resource pattern as the existing statement — no
change in bucket coverage, only in action set.

## Why the earlier PHP-side probe (_s3-probe.php) worked

Our diagnostic earlier this session did listObjectsV2 + headObject
against the bucket via the SDK from a PHP-FPM worker — both of which
only need s3:GetObject / s3:ListBucket. It never called getObjectAcl,
so the missing permission wasn't surfaced by that test. flysystem_s3's
stream wrapper is the first thing in the request path that actually
calls it.

## Rollout — IAM-only, no compute cycling

  cd /path/to/repo
  make deploy-iam ENV=sandbox

IAM policy changes take effect immediately for existing sessions
(no session refresh needed on already-running EC2 instance profiles —
the credentials AWS returns to the instance metadata service pick up
policy updates on the next credential rotation, which happens every
few minutes automatically).

Then hit any /_flysystem/s3/... URL to verify.

## Prod safety

Change applies to every env this template deploys (uses the
EnvironmentName wildcard). That is the right blast radius:

- prod's PHP compute role gains the same two actions on prod's media
  bucket. Since prod already runs flysystem_s3 (that's the whole
  reason we're wiring sandbox to match), those actions are already
  in use on prod today (via whatever bespoke IAM prod was set up
  with) — this template's `${EnvironmentName}-drupal-media-*` scope
  keeps each env restricted to its own bucket.
