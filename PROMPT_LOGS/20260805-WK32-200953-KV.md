## §4/§7.3 — Network placement (the big one)

Original draft put migrate-host in the default VPC parallel to
deploy-host, adding cross-VPC peering + FSx/RDS/Valkey ingress
rules — mirror-image complexity of cf-deploy-peering.yaml.

Kurt's insight: migrate-host is ephemeral, scoped to a single
migration window. It doesn't need to survive destroy-all like
deploy-host does. So put it IN the project VPC (private subnet)
and get direct SG-based RDS access for free.

Cascade of simplifications:
- No peering resources
- No cross-VPC SG references
- No cf-migrate-peering.yaml
- Zero FSx access (see §8 change below — dump staging moved to
  local disk)
- Zero Valkey access (Drupal caching isn't part of migration)
- SSM SendCommand between deploy-host and migrate-host goes over
  AWS APIs, not the VPC network — so peering isn't needed for the
  control plane either

Net: cf-migrate-host.yaml goes from ~4 SG ingress rules across
FSx/RDS/Valkey to ONE inline rule (RDS 5432 from migrate-host SG).

Documented as new Appendix C.3 so future-me can't reintroduce the
original mistake.

## §4/§6/§8 — Dump staging path

Original draft carried the deploy-host convention (dump at
/var/www/mysql/zinew.sql on FSx). Kurt caught it: on deploy-host
that's an FSx path because the 20 GiB root can't hold multi-GiB
dumps. On migrate-host (40 GiB high-IOPS gp3), local disk has
plenty of room.

Changes:
- Dump path becomes /var/tmp/migration/zinew.sql (local disk)
- Drop nfs-common package from bootstrap
- Drop use-env sandbox boot step (no FSx to mount)
- Drop use-env and valkey-env helpers (unneeded)
- Add /var/tmp/migration/ mkdir to bootstrap
- restore-mysql.sh dispatch defaults DUMP_LOCAL_PATH when
  HOST_STACK=cf-migrate-host

## §10.3 — Phase order (overlap deploy with preflights)

Kurt: phases -2/-1/0 (refresh-env, preflight, db-backup) don't
need the migrate-host, so they can run CONCURRENTLY with the CFN
deploy instead of blocking on it.

Original: deploy → wait → preflights → migrations
Revised:  deploy (background) → preflights (concurrent) → wait
          (join) → migrations

Expected win: 2-3 min per migrate-db-all run. Small but clean.
