feat(install-drupal): warm OS resolver + ALB path at end of install

Kurt's idea 2026-08-04: the site is fully serving by the end of
install-drupal (vhost published, drush verify passed, .installed
marker written). That happens ~15 min into migrate-full-all, before
pgloader even starts. If we fire ONE throwaway curl against the
public DNS name at that moment, the deploy-host's DNS resolver
populates its positive cache with the Route 53 alias, and the
ALB → nginx path gets exercised end-to-end (target-health warmup,
TLS handshake caching, etc.).

By the time migrate-full-all finishes 60-90 minutes later and the
final smoke-test-public runs, the resolver has been positive-caching
for an hour and the ALB path is fully warm. That test now hits on
attempt 1 every time — the retry+flush safety net we added in
commit 84d3e08 becomes purely a fallback for unusual environments.

Preventive fix complementing the reactive fix already in place:
- Preventive (this commit): prime the DNS + ALB paths NOW so they're
  warm later.
- Reactive (84d3e08): retry + resolver-flush when a race happens
  anyway (weird DNS servers, cache-forwarders, etc.).

Both cost near-zero. Cache-flush + one HEAD request is under a
second. Failures are strictly best-effort — a broken warm-up doesn't
kill install-drupal; the final smoke-test remains authoritative.

OS-detect matches smoke-test-public's flush block:
  - macOS: dscacheutil -flushcache + killall -HUP mDNSResponder
  - Linux (systemd-resolved): resolvectl flush-caches
  - Linux (older systemd): systemd-resolve --flush-caches
All via sudo -n so no password prompt.

Placement: between the write-install-marker step and the completion
summary, so the warm-up runs after the install is authoritatively
"done" and appears in logs right before the summary block.
