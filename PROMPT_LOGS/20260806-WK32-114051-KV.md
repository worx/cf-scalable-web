Great question — let me explain when parallel-agent work actually helps vs. when it just adds coordination overhead. Then I'll apply that specifically to this refactor.

## Agents: when they earn their keep

**Where they shine:**
- Work is genuinely independent (no shared state, no shared file, no output-feeds-next-input)
- Output would clutter my context if I did it myself (e.g., searching for one grep pattern across 500 files)
- Diverse perspective is the whole point (adversarial code review, security review)
- Long-running research that runs while I work on something else ("go read every CFN template and tell me which ones export a security-group ID")

**Where they don't:**
- Sequential dependencies (A → B → C, no way to skip)
- Small tasks (spawning + prompting an agent costs more than doing it yourself in 30 seconds)
- Iterative back-and-forth where each step informs the next
- Anything requiring judgment I'd want to make myself

## For THIS refactor: mostly linear, with a few parallel spots

The rollout in §11 has verify-gates between phases — those are inherently serial (Phase 2 shouldn't start until Phase 1 is proven green). Inside each phase, most work references other work being written (Makefile targets need CFN output names, CFN templates need SG IDs matching Makefile variables). Divergence risk when written by two workers.

**Where parallel actually helps here:**

1. **Phase 2 + Phase 3 concurrent** — best win. Phase 2 is on-migrate-host tuning (my.cnf, restore-mysql wrap, pgloader template). Phase 3 is on-deploy-host dispatch changes (HOST_STACK env-var + Makefile targets). Completely independent. Could genuinely run in parallel.

2. **Code review during Phase transitions** — after Phase 1 code lands, a `code-reviewer` agent can sweep it while I start Phase 2. Any issues surface in ~5 min; I address them at Phase 2's verify-gate.

3. **Research forks for ambiguity** — e.g., "before I write the IAM section of cf-migrate-host, `fork` an agent to grep for every place cf-deploy-host's `AdministratorAccess` is actually used, so I can decide if I can scope migrate-host tighter." That's a Phase 1 detail worth agent-delegating; it takes me 5 min of grep or 30 sec of fork-then-wait.

**Where parallel would hurt here:**
- Within Phase 1 itself: writing cf-migrate-host.yaml + bootstrap.sh + Makefile targets in parallel = 3 workers making tiny consistency mistakes with each other (parameter names, path names, output-key names). Not worth it. Serial + fast is faster overall.

**Then Phase 4 integrates** — serial again, ties everything together.

**Then Phase 5** — deploy-host shrink, small, serial.
