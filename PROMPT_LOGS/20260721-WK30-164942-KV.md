## Verification after refresh completes

```bash
# 1. Confirm the newly-launched instances are running the current AMI:
aws --profile ZI-Sandbox autoscaling describe-auto-scaling-groups \
  --auto-scaling-group-names sandbox-php83-asg \
  --query "AutoScalingGroups[0].Instances[?LifecycleState=='InService'].[InstanceId,LaunchTemplate.Version]" \
  --output table --region us-east-1
```

Then pick any instance ID from that list and SSM in to confirm the env var arrived:

```bash
aws --profile ZI-Sandbox ssm start-session --target i-XXXX --region us-east-1
# once in:
grep AWS_S3_BUCKET /etc/php/8.3/fpm/pool.d/www.conf
# expected: env[AWS_S3_BUCKET]    = "sandbox-drupal-media-kv-worxco"

# Confirm PHP-FPM workers actually see it:
sudo -u www-data php -r 'echo "AWS_S3_BUCKET=" . getenv("AWS_S3_BUCKET") . PHP_EOL;'
# expected: AWS_S3_BUCKET=sandbox-drupal-media-kv-worxco

# Bonus — confirm the IAM instance role can hit the bucket:
sudo -u www-data php -r '
require "/var/www/drupal/vendor/autoload.php";
$c = new Aws\S3\S3Client(["region" => "us-east-1", "version" => "latest"]);
$r = $c->listObjectsV2(["Bucket" => getenv("AWS_S3_BUCKET"), "MaxKeys" => 3]);
foreach ($r["Contents"] as $o) echo "  " . $o["Key"] . "\n";
' 2>&1 | head -10
```

If all three print what's expected, PHP-FPM side is fully wired.

## One remaining step for Drupal to actually USE it

Even once PHP-FPM sees `AWS_S3_BUCKET`, Drupal itself won't read it until `settings.php` on FSx has the `$settings['flysystem']` block. That's the `inject-flysystem-config.sh` step:

```bash
# on deploy-host:
cd /home/ubuntu/projects/cf-scalable-web
git pull
sudo bash scripts/deploy-host/inject-flysystem-config.sh
```

You can do that any time — before or after the refresh finishes. It's a `settings.php` edit on FSx, no compute-side dependency.

Once BOTH pieces land (env var on PHP-FPM boxes + flysystem block in settings.php), the wiring is complete. Sandbox Drupal *can* resolve s3:// URIs against the sandbox media bucket — but nothing visibly changes yet, because your current sandbox DB doesn't have any s3:// entries in `file_managed`. Those arrive when you run the DB migration per `zesty-plotting-squid`.
