Between that and Phase 0's db-backup, DNS/ALB/target-health are already stable. Fire a warm-up curl there and by the time smoke-test-public runs 60+ min later, the resolver's had literally an hour to positive-cache. Never flakes again.

**This is complementary to the retry+flush we just added, not a replacement.** Warm-up = preventive (avoid the race). Retry+flush = reactive (handle it if the race still happens). Both cost near-zero.

**Two possible places to add the warm-up:**

- **End of `install-drupal.sh`** (universal): a single `curl -sI --max-time 10 https://$SITE_NAME/ >/dev/null 2>&1 || true` at the tail. Runs on the deploy-host. Primes the deploy-host resolver + ALB path. Fires for EVERY install-drupal invocation (AUTO=yes branch, install-drupal-full, manual). Cleanest, most universal.

- **In `migrate-db-all` between Phase -1 and Phase 0** (migration-flow-specific): does the same thing but only when going through migration. Scoped, but misses standalone install cases.

I'd go with the first — one place, universal effect, ~3 lines added.
