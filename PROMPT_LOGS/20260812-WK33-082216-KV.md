fix(dispatch): treat SSM's null-status transient as "keep polling"

Caught 2026-08-12 during full-test-cycle.sh run: dispatch-db-backup
bailed with "ERROR: dispatch-db-backup failed with status: None" while
the underlying SSM command completed successfully — DB rename WORKED
(`OK: renamed drupal → drupal_backup_20260812_131718`), but the outer
dispatch script exited 1 anyway, killing the whole migration flow.

Root cause: SSM's get-command-invocation returns the Status field as
null during a brief window right after send-command (before AWS has
settled a status). `aws cli --output text` prints null as literal
"None". The polling case matched:

  InProgress|Pending|Delayed) # continue polling

  Failed|Cancelled|...)       # done, failed
  *)                          # unknown status — bail immediately

"None" fell into the wildcard branch → loop broke on first poll →
false-positive failure.

Fix: add `None` and `""` (empty string, defensively) to the polling-
continue list. Both mean "AWS hasn't assigned a status yet, wait
and re-poll."

Race is narrow (few hundred ms after send-command) but reproducible
on freshly-invoked send-commands under normal load. Doesn't affect
any long-running command past the first poll cycle.
