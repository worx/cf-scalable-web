### 20:59:03 - Response

Good design instinct. Publish-dns is the natural home for it — put the warmup where the DNS change happened, not somewhere upstream that ran against stale state. And the "don't care if it fails" framing is exactly right: this is a resolver-cache prime, not a validation.

One small clarification on the mechanics so we're aligned on what a warm-up curl actually buys us:

- **Doesn't shorten remote resolver TTLs.** Remote caches expire when *their* TTL clock hits zero, and their clock started when *they* first cached an answer — a curl from our machine doesn't touch their caches.
- **Does warm THIS machine's resolver cache** — first curl forces our local resolver to query Route 53 authoritatively and get the new answer, so any script that runs on the same host immediately after (like smoke-test-public) sees the fresh record.
- **Does validate the record is publishable-and-resolvable end-to-end** — catches an SOA MIN gotcha or misconfigured alias before you get bit by it later.

Kurt's mental model of "start countdown timers" isn't quite right — remote clocks are already ticking, we can't accelerate them — but the CONCLUSION (add warm-up to end of publish-dns) is sound.

**Two edits worth doing in one change:**

1. Add `curl -s -o /dev/null -w '%{http_code}\n' --max-time 5 --retry 3 https://${SITE_NAME}/ || true` at the end of `publish-dns` — warmup our resolver, prints the HTTP code for the human's eyeball (they can see "302 as expected pre-migration" or "200 post-migration"), never fails the target.

2. Remove the warm-up curl from the end of `install-drupal.sh` — redundant with publish-dns's version, and always fires against stale-or-non-existent DNS from install-drupal's position in the pipeline.

Want me to make that change now (small, self-contained) or drop it as a task for after Phase 3 timing test finishes? I'd lean toward doing it now — it's contained, doesn't touch migration-critical paths, and keeps `publish-dns` clean for the next full-cycle test.
