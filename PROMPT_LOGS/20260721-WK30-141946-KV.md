fix(migration): sync-s3-media preflight — real head-bucket + visible errors

Two-part bug that made the last three sync-s3-media runs look like IAM
misconfig when the IAM was fine all along:

## Bug 1 — invalid CLI flag

Both preflight checks were written as:

  aws s3 ls "s3://$BUCKET/" --region "$REGION" --max-items 1

`--max-items` is a `s3api list-objects-v2` option, NOT `s3 ls`. The AWS
CLI rejects it with a ParamValidation error before ever reaching S3:

  aws: [ERROR]: An error occurred (ParamValidation):
       Unknown options: --max-items,1

Exit code non-zero → preflight fails → misleading error to operator.

## Bug 2 — silent stderr

Both checks piped stderr to `/dev/null`:

  if ! aws s3 ls ... >/dev/null 2>&1; then
    log_error "Cannot read from source bucket ..."

So the real AWS error (ParamValidation, AccessDenied, whatever) was
invisible. Operator saw only the generic "Cannot read" message and
went hunting IAM. In this particular case we chased three separate
IAM commits — Prod-side ReadProdMediaSource, Sandbox-side MediaBucket
policy, Prod-side WriteSandboxMediaTarget — all of which were
correct additions on their own, but none of which were the actual
root cause. The script's own preflight was broken.

## The fix

Switch to `aws s3api head-bucket` — the AWS-canonical "does this
bucket exist and can I access it" call. Requires `s3:ListBucket`
(same as any bucket-listing check would). Extremely lightweight —
HTTP HEAD, no object enumeration.

Also capture stderr into a local var and surface it in `log_error`:

  ERR=$(aws s3api head-bucket ... 2>&1) || {
    log_error "Cannot read ..."
    log_error "  AWS error: $ERR"
    ...
  }

So the actual AWS message ("An error occurred (403) when calling the
HeadBucket operation: Forbidden") appears in the log. Future
misconfigs will report themselves instead of masquerading as
"permission problem."

## Target-bucket check hint improvements

Also expanded the target-bucket error hint to remind operator that
cross-account S3 requires BOTH sides — the sandbox bucket policy AND
the prod-side jumpbox identity policy. Original hint only mentioned
the sandbox side (which alone isn't sufficient — a lesson we just
learned the hard way three commits ago).

## Rollout — script only, no CFN

  git pull
  cd migration
  make sync-s3-media

_ssm-run-jumpbox.sh re-uploads jumpbox scripts to S3 on every run,
so the fixed sync-s3-media.sh reaches the jumpbox as part of the
normal dispatch. No stack redeploy needed.

  stderr surfacing, expanded target-side hint
