### 20:54:56 - Response

**Found it — but different bug than I expected.** The Route 53 record EXISTS, but points to the **OLD** ALB from before destroy-all:

- **Record targets:** `sandbox-alb-1269500160.us-east-1.elb.amazonaws.com` (destroyed)
- **New ALB is actually:** `sandbox-alb-1559425261.us-east-1.elb.amazonaws.com` (active)

The old ALB name doesn't resolve anymore, hence the wget failure. Route 53 aliases are operator-owned by design (they survive destroy-all — hence the record still exists), but the target inside the alias needs to be re-pointed after any ALB churn.

## Fix — one command

```bash
cd ~/projects/cf-scalable-web
make publish-dns ENV=sandbox
```

This UPSERTs the alias to point at the current ALB. Then wait 1-2 min for propagation (usually seconds since it's a Route 53 change to your own zone, no ripple):

```bash
# Verify:
dig +short @8.8.8.8 sandbox.envs.zoning-info.com
# expected: a few AWS IPs (from the alias to sandbox-alb-1559425261.…)

# Then browser or wget:
wget -O /dev/null https://sandbox.envs.zoning-info.com/
```

## Why this happened — Phase D backlog territory

`install-drupal-full` (the higher-level target) includes `publish-dns` as step 5 of its 6-step chain. But `install-drupal` (base) does NOT. `migrate-db-all`'s `AUTO=yes` fallback invokes `install-drupal` (base), not `install-drupal-full`. So the DNS publish step never fired on your fresh sandbox.

**Fix option for Phase D:** either
1. Change `migrate-db-all`'s `AUTO=yes` to call `install-drupal-full` instead of `install-drupal` — one-line Makefile change, but install-drupal-full is 5-7 min vs install-drupal's 3-5 min because of the DNS + smoke-test additions
2. Add a Phase 9 to migrate-full-all that specifically does `publish-dns` — cleaner separation
