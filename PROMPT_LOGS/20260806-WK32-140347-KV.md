feat(both hosts): auto-restore operator state from S3 on first boot

Closes the second half of the destroy → deploy loop for both
deploy-host and migrate-host. Auto-backup-on-destroy was already
wired in destroy-{deploy,migrate}-host; the matching auto-restore-
on-first-boot was never built. Kurt caught it: destroyed migrate-
host, redeployed, SSM'd in and had zero shell history despite the
backup having been taken.

Both bootstraps now add an "Auto-restore operator state" step just
BEFORE the marker-file step:

  1. head-object the config/{host}-latest.tar.gz key in the
     matching backups bucket.
  2. If present  → run scripts/{host}/restore-state.sh with
     CONFIRMED=yes.
  3. If absent   → log "first-ever deploy" and skip.
  4. If restore-state.sh fails → WARN and continue (box is still
     functional, operator can retry manually).

Design principle: bootstrap MUST NOT fail because of a restore
issue. A working-but-empty box is a much better UX than a bricked
deploy. If restore fails, the operator has an obvious next step
(`make restore-{host}`).

Restore runs BEFORE marker write so wait-{host}-ready.sh doesn't
signal "ready" until state is loaded — no race where Kurt SSHs in
mid-restore.

Files Modified:
- scripts/migrate-host/bootstrap.sh (added restore step + block)
- scripts/deploy-host/bootstrap.sh  (identical treatment for parity)

Verified: bash -n clean on both. restore-state.sh already exists,
honors CONFIRMED=yes as a passthrough (no interactive prompts today,
future-proof).
