### 15:06:48 - Response

Found it. `psql-env` connects as `dbadmin` (RDS master, line 42 of the script), but `drupal_user` owns the DB. Postgres `ALTER DATABASE ... RENAME` requires the caller to be the owner — dbadmin isn't.

Fix: grant dbadmin membership in `drupal_user`, then transfer ownership before the rename. Cleaner (and PG-version-agnostic) than SET ROLE gymnastics.

```bash
STAMP=$(date -u +%Y%m%d_%H%M%S)
BACKUP_DB="drupal_backup_$STAMP"
echo "Backup DB name will be: $BACKUP_DB"

psql-env sandbox -d postgres <<SQL
-- One-time: let dbadmin act on drupal_user's objects
GRANT drupal_user TO dbadmin;

-- Take ownership of drupal so we can rename it
ALTER DATABASE drupal OWNER TO dbadmin;

-- Kick active connections off drupal
REVOKE CONNECT ON DATABASE drupal FROM PUBLIC, drupal_user;
SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname='drupal' AND pid<>pg_backend_pid();

-- Rename current drupal → backup
ALTER DATABASE drupal RENAME TO $BACKUP_DB;

-- Create fresh empty drupal DB
CREATE DATABASE drupal OWNER drupal_user;

-- Give the backup DB back to drupal_user for cleanliness
ALTER DATABASE $BACKUP_DB OWNER TO drupal_user;

-- Restore CONNECT
GRANT CONNECT ON DATABASE drupal TO drupal_user;
GRANT CONNECT ON DATABASE $BACKUP_DB TO drupal_user;

\l
SQL
```

## Notes worth knowing

- **`GRANT drupal_user TO dbadmin` is persistent** across sessions. That's actually useful — future `psql-env` calls can manage drupal_user's objects without redoing this. If you ever want to revoke: `REVOKE drupal_user FROM dbadmin;`.
- **Everything runs in ONE psql session via heredoc** — state is consistent. If any statement in the middle fails, Postgres continues (no transaction wrapper because `ALTER DATABASE ... RENAME` and `CREATE DATABASE` can't run in transactions).
- **SQL comments (`--`) are consumed by psql**, so zsh's lack of `#` comment support isn't an issue here.
