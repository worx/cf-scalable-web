feat(migration): _ssm-run-deploy-host.sh + walk-away dispatch targets

Follow-up #9. Mirror of _ssm-run-jumpbox.sh for the sandbox side. Enables
kick-off-and-walk-away migrations from Mac without tmux ceremony.

## The problem this solves

`make restore-mysql` and `make run-pgloader` currently require an
interactive SSM session on the deploy-host. SSM Session Manager has
~15-20 min idle timeout — a full run-pgloader (~2 hours) has to run
inside tmux to survive, and even then the operator's terminal has
to be alive to see progress or fetch results.

Discovered live during the 2026-07-17 test migration: a mid-flight
pgloader run got killed when the SSM session timed out. Fix was to
restart under tmux, which works but adds ceremony.

## The pattern

New `migration/scripts/_ssm-run-deploy-host.sh` runs on Mac and:

  1. Looks up sandbox migration bucket + deploy-host instance ID via CFN
  2. Uploads `migration/scripts/_common.sh` + the target script (fresh
     from local checkout — no reliance on deploy-host having pulled
     the latest git)
  3. Dispatches via `aws ssm send-command`, which spawns a runner ON
     the deploy-host — the runner is SSM's own process, immune to
     Mac-side interrupts (session timeout, sleep, lid close, Wi-Fi
     drop, laptop lost at sea)
  4. Polls `get-command-invocation` every 30s (configurable) for up
     to 2 hours (configurable). Ctrl-C detaches — remote work
     continues; poll again later with the printed CommandId
  5. Fetches stdout/stderr on completion and displays

Simpler than `_ssm-run-jumpbox.sh` because we're single-account (no
cross-account credential dance). Uses ZI-Sandbox profile throughout.

## New Mac-side make targets

- `make dispatch-restore-mysql` — kicks restore-mysql on deploy-host
- `make dispatch-run-pgloader` — kicks run-pgloader on deploy-host

Both accept the standard env overrides (CONFIRMED DRY_RUN
MIGRATION_DB_NAME PGLOADER_HEAP_MB POLL_TIMEOUT) and pass them
through to the remote script via the SSM `env KEY=VAL` prefix.

Existing `make restore-mysql` / `make run-pgloader` targets are
preserved — they're now the "interactive from an SSM session"
variant. Operators pick:
  - `dispatch-*` when running unattended (overnight, from a laptop
     that goes to sleep, from CI, etc.)
  - Non-dispatch when already SSH'd in and wanting to see live output

## Why the dispatcher is scoped to migration/ scripts only

Currently only migration scripts source `_common.sh`. Top-level
deploy-host scripts (db-backup.sh, install-drupal.sh, etc.) are
standalone. Building a general-purpose dispatcher that handles both
would need to either:
  - Detect whether _common.sh is needed (fragile)
  - Always upload it (unnecessary for standalone scripts)

Deferred to when we actually need it. For now: migration-focused.
The eventual `migrate-db-all` uber-target (follow-up #10) only needs
to chain migration + clear-drupal-cache, both of which are already
solved (dispatcher for migration, existing inline pattern for
clear-drupal-cache).
