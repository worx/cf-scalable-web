### 09:52:31 - Response

Two great questions worth answering separately.

## What Drupal's hash_salt actually does

Not encryption. It's a **per-site shared secret** used to sign or derive cryptographic material for a bunch of things that need "this token came from THIS site":

- **CSRF form tokens** — every form's hidden token is HMAC(form_id + session_id + hash_salt). Different salt → tokens don't validate.
- **Password reset URLs** — `/user/reset/UID/timestamp/HASH` — that HASH is HMAC-signed with hash_salt. Salt changes, all outstanding reset emails become dead links.
- **Image style URLs** — those `?itok=...` query params on `/sites/default/files/styles/thumbnail/...` are signed with hash_salt. Salt changes, existing cached image URLs 403 until Drupal regenerates them.
- **Session cookie validation** (Drupal 9+) — some session-integrity checks HMAC with hash_salt.
- **API/webhook signatures** — third-party integrations that sign requests to Drupal often HMAC with hash_salt.
- **Some contrib module encryption** — key derivation for things like encrypted state.

None of it is data-at-rest encryption. It's all "prove this thing came from this site."

## Why sandbox's salt, not prod's

Same category as DB password, admin password, SSH keys — they're **per-environment secrets**, not per-installation-content. Migration copies DATA and CONFIG from prod. Migration deliberately does NOT copy sandbox's own identity.

If sandbox shared prod's salt:
- A password reset link emailed from prod would ALSO validate on sandbox (someone with the link + a route to sandbox could pwn accounts there)
- Prod's image URLs would work on sandbox (minor)
- Cross-env token bleed on any integration that trusts the salt

Sandbox is a test environment. It should be functionally similar to prod (same data shapes) but cryptographically independent (different identity). Users can log into prod and sandbox separately without one credential grant leaking to the other.

## About "restoring from local backup"

The `.BAK.<UTC>` isn't a random file we happened to find — it's a snapshot of `/var/www/drupal-private/` taken **immediately before** restore-private ran. That salt.txt was generated by `install-drupal.sh` when sandbox was first installed, and has been used continuously since. So the preserve-from-BAK path is really "keep sandbox's own salt across a data migration."

Reasoning by analogy with your other per-env secrets:
- `worxco/sandbox/drupal/db-password` — sandbox's, not prod's
- `worxco/sandbox/drupal/admin-password` — sandbox's, not prod's
- `worxco/sandbox/rds/master-password` — sandbox's, not prod's
- `/root/.ssh/*` (deploy-host) — sandbox's, not prod's
- `salt.txt` — sandbox's, not prod's ✓

The salt fits the pattern. It just happens to live on FSx in a plain-text file instead of in Secrets Manager — which is a known design wart called out in `docs/memory/salt-persistence-design.md`. The long-term fix is to move it to SSM SecureString like the other secrets, but that's a separate rework. For now: preserve-across-restore is the right behavior.

## Where prod's salt goes

Since prod's `private/` dump doesn't (usually) include salt.txt anyway — and even if it did, we deliberately overwrite with sandbox's version — prod's salt.txt never lands on sandbox. It stays where it belongs: on prod's FSx, doing prod's signing.
