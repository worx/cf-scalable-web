### 10:40:28 - Response

Both reasons compound. Two things happening:

**1. Your `type` filter hides most rows.** You filtered to `type IN ('php', 'commerce', 'views')`. But watchdog is Drupal's catch-all log for *everything*: user logins (`user`), page views (`access`), cron runs (`cron`), config changes (`system`), search indexing (`search`), etc. Between wid 29589 and 30569, most of those ~980 rows are probably `system`, `access`, or `cron` — filtered out by your query.

**2. Sandbox is writing new watchdog entries as you use it.** wid is a `SERIAL` (auto-incrementing) column. It doesn't get renumbered by the migration — pgloader preserves the existing wid values from prod's MySQL dump, and Drupal continues writing new rows starting from `max(wid)+1`. Every install-drupal + cache-clear + admin login + page view generates watchdog rows.

Rough timeline reconstructed from your data:
- **wid 29587-29589**: historical entries from PROD's watchdog table, captured in the prod DB dump
- **wid 29590 – 30568**: ~980 rows Drupal wrote on sandbox during install-drupal + migration + your admin browsing today
- **wid 30569-30571**: today's three division-by-zero errors from your `/admin/commerce` visits

**Confirm the theory** by looking at what fills the gap — same query without the type filter:

```bash
psql-env sandbox <<'SQL'
SET search_path = zinew;
SELECT wid, type, COUNT(*) OVER (PARTITION BY type) AS type_count
FROM watchdog
WHERE wid BETWEEN 29590 AND 30568
ORDER BY wid DESC
LIMIT 20;
SQL
```

You'll see the actual distribution — probably heavy on `system`, `access`, and maybe `page not found`.

**Aside:** Drupal's `dblog_cron()` normally trims watchdog to a max row count (default 1000 in `system.settings`) to prevent unbounded growth. You can eyeball your limit with `drush cget dblog.settings` on deploy-host. If it's disabled or set very high, watchdog just grows forever — normally not a problem, but if the table ever balloons, that's the knob.
