# Multi-Site Refactor: Phased Implementation Plan

## 1. Design decisions (recommendations)

**A. Directory layout — pick Option 1: `/var/www/&lt;site&gt;/{web,private,config}/`.**
The whole design pivots on this. A single subtree per site makes archive/rename/clone one `mv` (or one `zfs snapshot`), makes disk usage per site trivially observable (`du -sh /var/www/*/`), and eliminates 3 hardcoded siblings scattered through `install-drupal.sh:71-73`, `refresh-env-config:94`, and both restore scripts. Migration cost is one-time and mechanical.

**B. PHP-FPM env[] delivery — pick Option 2: single pool, settings.php sources per-site env file.**
Pool-per-site would multiply NLB target groups and PHP ASGs by N; a non-starter. Drupal's own multi-site pattern already uses per-directory `settings.php`, and it lets each site pick its DB, schema, salt, S3 bucket, and even Drupal version/patch set without touching PHP-FPM or nginx boot scripts. This also cleanly separates the layers Kurt wants separated: nginx picks PHP version, PHP-FPM stays generic, Drupal picks its data.

**C. DB naming — pick Option 1: DB name = site name** (with `-`→`_` for PostgreSQL identifiers, e.g. `zoning-info` → `zoning_info`). One less concept for operators. Backup DB naming stays `&lt;site&gt;_backup_&lt;UTC&gt;`.

**D. Backward compat — NEEDS KURT'S INPUT.** Recommend renaming to the real client site name (e.g. `zoning-info`) as part of Phase 1 because (a) the current `drupal` name is a placeholder that will be misleading the moment a second site exists, (b) the jumpbox already hardcodes `zoning_info_platform` in migration paths, and (c) doing the rename simultaneously with the namespace refactor is one migration, not two. Cost: `remove-drupal` + reinstall in sandbox; production hasn't been cut over yet per repo state. If Kurt prefers zero data movement, use `SITE=drupal` as-is and defer rename to Phase 5's rename tooling.

**E. MVP scope acknowledged.** The plan below builds backup/restore in a shape that makes clone/archive/rename mechanical follow-ons — same site-parameterized entry points, different verbs.

## 3. Phased implementation

**Phase 1 — Namespace + settings pivot (single site, no behavior change).**
Parameterize `install-drupal.sh` on `SITE`. Change `INSTALL_DIR`/`PRIVATE_DIR`/`CONFIG_DIR` to `/var/www/$SITE/{web,private,config}`. Rewrite the settings.php heredoc to `require` a per-site env file (`/etc/worxco/sites/$ENV/$SITE.env`) rather than trusting FPM-level env[]. Move D-decision migration (rename `drupal` → `&lt;real-site&gt;`) into a small one-shot `rename-legacy-site` script that shuts down PHP, `mv`s the tree, renames the DB via the existing backup/restore rename pattern, and re-runs vhost publish. **Deliverable: existing site still works, now identified by its real name, at its new paths.**

**Phase 2 — Vhost + PHP-FPM decoupling.**
Consolidate the two `drupal.conf` writers into a single `scripts/publish-site-vhost.sh SITE=&lt;X&gt; ENV=&lt;E&gt;` (delete the heredoc in `install-drupal.sh:660`, keep only the one in publish script; make install call it). Vhost filename becomes `&lt;X&gt;.conf`. Strip the per-site env[] block from `image-builder/configs/configure-php.sh:135-180` — keep only truly cross-site infra (RDS endpoint, cache endpoint/auth, ENVIRONMENT_NAME). Per-site DB/salt/site-name now flow exclusively via settings.php reading its per-site env file. **No FPM reboot needed for site changes after this.**

**Phase 3 — Second site + backup/restore.**
Refactor `cf-app-drupal.yaml` → `cf-app-site.yaml` parameterized on `SiteName`; deploy one stack per site (`app-site-&lt;env&gt;-&lt;site&gt;.json` parameter files). Widen IAM wildcard to `${prefix}/sites/*/*`. Add `install-site SITE=X ENV=E` make target (thin wrapper over the now-parameterized install-drupal.sh). Add `SITE=` arg to `db-backup.sh`/`db-restore.sh` (they already accept a db_name — just default it from `/etc/worxco/sites/&lt;E&gt;/&lt;X&gt;.env`). Add `files-backup SITE=X` / `files-restore SITE=X` that snapshot `/var/www/&lt;X&gt;/` to S3 as `site-backups/&lt;site&gt;/&lt;UTC&gt;.tar.zst`. **Deliverable: two coexisting sandbox sites, each independently backupable and restorable, verified below.**

**Phase 4 — Migration pipeline site-scoping.**
Namespace all dump keys under `dumps/&lt;SITE&gt;/`; make `SITE=` required on every migration target; parameterize jumpbox `DRUPAL_ROOT` (currently pinned to `zoning_info_platform`). Restore scripts already accept `TARGET_DIR` — thread `SITE` through the dispatch layer. Un-pin `ENV=sandbox` in `migrate-db-all`.

**Phase 5 (DEFERRED, but design-ready) — clone/archive/rename/apply-updates.**
Given Phase 1-3's shape: `clone SITE=A NEW=B` = `zfs snap /var/www/A → /var/www/B` + backup/restore-into-new-db + `install-site` skipping fresh scaffold; `archive SITE=X` = `files-backup` + `db-backup` + drop DB + `mv /var/www/X /var/www/.archive/X-&lt;UTC&gt;`; `rename SITE=A NEW=B` = same DB rename pattern already in db-backup.sh + fs `mv` + regenerate vhost/env/SSM. All work at the per-site layer with no PHP-FPM reboot.

## 6. Non-goals for MVP (explicit deferrals)

- **Web UI, self-service provisioning, per-site cron schedules, per-site Valkey namespace/prefix.**
- **Production cutover** — MVP proves in sandbox only.
