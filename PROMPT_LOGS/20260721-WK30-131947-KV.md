feat(migration): grant jumpbox both halves of cross-account media sync

The direct sync-s3-media path (prod → sandbox media bucket, no
intermediate hop) needs THREE IAM grants; when we pivoted to direct
sync we only added one, and the first run surfaced both gaps in
sequence:

1. Prod side, read:  jumpbox role can read from s3://zi-documents/
   → Phase 1 error: "Cannot read from source bucket s3://zi-documents/"
2. Sandbox side, resource policy: MediaBucket allows the jumpbox role
   → Already in place (98bec6c on cf-storage-s3.yaml)
3. Prod side, write: jumpbox role can write to s3://sandbox-drupal-media-kv-worxco/
   → Phase 1 error: "cannot list ... sandbox-drupal-media-kv-worxco"

Cross-account S3 requires the grant on BOTH sides. The sandbox bucket
policy alone isn't enough — the jumpbox role's identity policy also
has to allow the action on that resource. Otherwise ListBucket fails
during `aws s3 sync` preflight and the sync never starts.

This commit adds both #1 and #3 in one shot — parameterized so
non-migration deployments of this template (e.g. a jumpbox for a
different data ferry) attach neither by default.

## Two new optional parameters (both default '')

  ProdMediaSourceBucket        → grants s3:ListBucket + s3:GetObject
                                  on that same-account bucket
  SandboxMediaTargetBucket     → grants s3:PutObject + PutObjectAcl
                                  + GetObject + ListBucket
                                  + DeleteObject on that
                                  cross-account bucket

Each is gated by its own condition (HasProdMediaSource /
HasSandboxMediaTarget) and creates a standalone AWS::IAM::Policy
resource attached to the existing JumpboxRole. Standalone Policy
resources are the only way to get truly-conditional IAM policies —
Role.Policies array entries cannot be conditionally omitted.

## Params file update (single set for our migration use case)

  ProdMediaSourceBucket:        zi-documents
  SandboxMediaTargetBucket:     sandbox-drupal-media-kv-worxco

## Directionality — no accidental writes back to prod

The prod-side policy is READ-ONLY (Get/List only, no Put/Delete). The
sandbox-side policy allows write on the sandbox bucket only. There is
no combination of these grants that would let the jumpbox modify prod
media.

DeleteObject on the sandbox side is included so
`make sync-s3-media DELETE_ORPHANED=yes` works without needing a
second stack deploy.

## Rollout

  cd migration
  make deploy-jumpbox       # IAM-only, ~30 sec, no instance cycling
  make sync-s3-media        # should now sail through Phase 1 into sync
