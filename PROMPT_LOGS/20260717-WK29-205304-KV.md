Kurt's ask: don't rely on operator memory or read-the-docs to remember

## What was covered before

Every remote script (runs on jumpbox or deploy-host) already self-logged
via `log_init` + `log_upload_and_exit` trap:

  migration/scripts/jumpbox/{dump-mysql, dump-codebase, dump-files, dump-private}.sh
  migration/scripts/deploy-host/{restore-mysql, run-pgloader, restore-files, restore-private}.sh

Logs land in `/var/log/worxco-migration/<script>-<UTC>.log` on the
remote AND get uploaded to `s3://<migration-bucket>/logs/YYYY-MM-DD/`
on script exit. Full audit trail.

## What was NOT covered

Dispatcher scripts (Mac/deploy-host side) that DRIVE the remote work:
their output only lived in the operator's terminal scrollback. If the
terminal closed or tmux ate the output, it was gone.

## Fix — log_init added to 7 dispatchers

- `migration/scripts/_ssm-run-deploy-host.sh` (used by dispatch-restore-mysql, dispatch-run-pgloader, dispatch-restore-files, dispatch-restore-private)
- `migration/scripts/_ssm-run-jumpbox.sh` (used by dump-*)
- `scripts/dispatch-db-backup.sh` (used by dispatch-db-backup + migrate-db-all)
- `scripts/clear-drupal-cache.sh`
- `scripts/admin-login-url.sh`
- `scripts/install-drupal-remote.sh`
- `scripts/publish-drupal-vhost.sh`

Each now writes a durable log every time it runs. Location depends on
OS (see `_common.sh` change below): `/var/log/worxco-migration/` on
Linux (deploy-host / jumpbox), `/tmp/worxco-migration/` on Mac
(no sudo prompt, no ~/.local pollution).

## _common.sh changes

**OS-aware default log dir.** `log_init` now checks `uname -s` and
defaults to `/tmp/worxco-migration` on macOS instead of trying to
`sudo mkdir /var/log/...`. Overridable with `WORXCO_LOG_DIR` env
var if operator wants a different location.

**New stderr-only mode.** `log_init "<name>" stderr` tees only stderr
to the log file, leaving stdout untouched. Needed for scripts like
`dispatch-db-backup.sh` whose stdout carries machine-parseable output
(the newly-created backup DB name) that a caller captures via
`BACKUP_DB=$(dispatch-db-backup.sh sandbox)`. Without this mode, tee'd
stdout would pollute the caller's capture with status noise.

Default mode remains "both" (stdout + stderr → tee → log). Only
dispatch-db-backup uses "stderr" today.

## scripts/_common.sh (new)

Thin wrapper that re-sources `migration/scripts/_common.sh`. Reason:
`migration/scripts/_common.sh` is the canonical file because it also
ships to remote hosts alongside the migration scripts via the SSM
upload machinery. Top-level scripts don't share that upload flow but
need the same helpers, so this wrapper gives them a nearby _common.sh
without an ugly `../migration/scripts/...` path in every `source` line.

## What the operator sees now

Before:
```
make dispatch-restore-mysql   # output lives only in terminal
                              # no file written
```

After:
```
make dispatch-restore-mysql
# → /var/log/worxco-migration/_ssm-run-deploy-host-restore-mysql-<UTC>.log
#   (on deploy-host — captures CommandId, poll progress, remote output)
# → also uploaded to s3://<bucket>/logs/YYYY-MM-DD/ on exit
```

The remote script itself STILL self-logs at its own path, so post-mortem
of a `migrate-full-all` run gives you:
  - The uber-target's tmux/nohup output (operator's responsibility if wanted)
  - Each dispatcher's log (auto-captured now)
  - Each remote script's log (auto-captured, already was)

Every layer of the stack has its own durable trail. No operator
memory / tee incantation required.
