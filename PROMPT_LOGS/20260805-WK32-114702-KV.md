## 6. What would benefit from more CPU/RAM

**MariaDB restore (`mysql &lt; dump.sql`)**
- Fundamentally single-threaded per-statement (one client → one connection → serialized inserts). More CPU cores don't help the client itself.
- **RAM** would help: raising `innodb_buffer_pool_size` (currently distro-default ~128 MB) to several GB dramatically reduces InnoDB flushing during index/PK inserts. Same for `innodb_log_file_size`, `tmp_table_size`, `max_heap_table_size`. **None of these are set today** — greenfield tuning opportunity on the new host.
- Disk: dump file is on FSx, InnoDB data on 20 GB root gp3 (baseline 3000 IOPS). A larger/gp3-provisioned-IOPS volume for `/var/lib/mysql` on the migrate-host would also help.

**pgloader**
- Scales with **RAM**: `--dynamic-space-size` (currently 4096 MB); `batch rows` / `prefetch rows` (currently 500 each — the per-worker in-flight row buffer); `batch size = N MB` (not set, defaults apply).
- Scales with **CPU**: `workers` (currently 2, default 4; per-table thread pool); `concurrency` (currently 1, i.e., one table at a time — raising to 2–4 would load multiple tables in parallel and is the single biggest wall-time win); also implicit `max parallel create index` (not set).
- Given a 16 GB / 4-vCPU host, plausible ranges: heap 8–12 GB, workers 4–8, concurrency 2–4, batch/prefetch back toward the pgloader defaults (~25000 / 1000) — the exact values that OOM'd on the 2 GB-swap deploy-host.
