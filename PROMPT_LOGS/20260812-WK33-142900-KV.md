## Task #34 explained

**The issue:**

`install-drupal-full` is a 4-step target that promises a full sandbox Drupal setup in one command:

1. `install-drupal-remote` — SSM-dispatches drush site:install to deploy-host, creates drupal_user, publishes vhost, reloads nginx
2. `smoke-test-drupal` — asserts HTTP 200 on the site via DNS-bypassed curl
3. `publish-dns` — Route 53 alias for sandbox.envs.zoning-info.com
4. `smoke-test-public` — asserts HTTP 200 through real DNS

**The problem — cold-start case:**

On a fresh env with NO prior migration, install-drupal writes settings.php pointing at PostgreSQL schema `zinew`. But `zinew` is empty until pgloader populates it. Drupal boots, queries key_value in the empty schema, finds nothing, decides it's "not installed," and returns HTTP 302 redirecting to `/core/install.php`.

Step 2 (`smoke-test-drupal`) sees 302 not 200 → exits red → whole target bails. Steps 3 (`publish-dns`) and 4 (`smoke-test-public`) never run.

**How it manifests:**

If someone runs `install-drupal-full ENV=sandbox` on a fresh sandbox that hasn't been migrated yet, they see a "failed" red X even though install-drupal itself succeeded. Then they have to know to run `make publish-dns` manually anyway.

**Why full-test-cycle.sh works around it:**

Instead of `install-drupal-full`, full-test-cycle.sh does the two useful steps separately in Phase 2:
```
make install-drupal-remote ENV=$ENV && make publish-dns ENV=$ENV
```
It skips the two smoke-test steps (they'd fail cold-start) and defers those to Phase 11, AFTER the migration has populated `zinew`.

**Options for a real fix:**

- **A**: Teach `smoke-test-drupal` a `SKIP_ON_UNMIGRATED=yes` mode that accepts the 302→install.php as valid
- **B**: Split `install-drupal-full` into two variants (cold-start vs steady-state)
- **C**: Reorder to drop the smoke tests from install-drupal-full entirely — make it just install + publish-dns
- **D**: Delete install-drupal-full and document the two-command replacement

**My honest read:**

Since **full-test-cycle.sh already handles the cold-start path correctly** and never invokes install-drupal-full, this bug only bites someone running install-drupal-full directly in a cold-start scenario — which is basically "someone who's not using full-test-cycle.sh but IS doing a fresh sandbox."

Realistically that's ~never. You use full-test-cycle.sh. Nobody else runs this project.

**Recommend: mark #34 as won't-fix, or delete `install-drupal-full` outright** so it can't lure someone into the confusing failure mode. If someone in the future wants a one-shot "install Drupal on an already-migrated env," they can run the two commands manually — the docs would be clearer than a target that only sometimes works.

Your call — mark it won't-fix, delete the target, or leave it pending. If you're pragmatic (which you've been), won't-fix is fine.
