**The key detail that tells us where to look**: `smoke-test-drupal` returned HTTP 200 (else the make command would have exited non-zero and you'd have seen a red error). But your browser returns 500. That's a real inconsistency between two clients hitting the same URL. **Only one code path differs between them: DNS resolution.**

- `smoke-test-drupal` uses `curl --resolve` to pin the ALB IP directly, bypassing DNS entirely.
- Your browser resolves `sandbox.envs.zoning-info.com` through your OS resolver + Route 53.

Most likely: your Mac's DNS cache has a stale entry from a previous sandbox deploy (a prior ALB IP that's now unhealthy or doesn't exist). curl --resolve dodges this; browser doesn't.

**When you're back, three quick diagnostics** (all from your Mac, ~30 sec total):

```bash
# 1. What is DNS actually resolving to right now?
dig +short sandbox.envs.zoning-info.com

# 2. What is the current ALB's actual IP?
dig +short $(aws --profile ZI-Sandbox cloudformation describe-stacks \
  --stack-name cf-scalable-web-sandbox-compute-alb \
  --query "Stacks[0].Outputs[?OutputKey=='ALBDnsName'].OutputValue" \
  --output text --region us-east-1)

# 3. Flush your Mac's resolver + retry via browser
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Then Cmd-Shift-R in browser
```

**If #1 and #2 differ** → Route 53 is out of sync with the current ALB. `make publish-dns ENV=sandbox` to fix (though we just ran it — maybe a race).

**If #1 and #2 match but browser STILL 500s after DNS flush** → it's a real app-layer issue. Could be some compute instance's PHP-FPM didn't restart cleanly. Try `curl -sL https://sandbox.envs.zoning-info.com/ -o /tmp/response.html && head -50 /tmp/response.html` — if we get the actual Drupal error page HTML, it'll tell us WHAT PHP saw.
