Same wrapper — Drupal's generic "unexpected error" page masks the real exception. The actual details are in the watchdog table on RDS. Since it's the same pattern we used to diagnose the commerce_remote_id class issue, same query:

```bash
make ssm-deploy-host
psql-env sandbox <<'SQL'
SET search_path = zinew;
SELECT wid, type, severity, LEFT(convert_from(variables, 'UTF8'), 800) AS vars
FROM watchdog
WHERE type IN ('php', 'commerce', 'views')
ORDER BY wid DESC
LIMIT 5;
SQL
exit
```

The `variables` column has the PHP exception class + message serialized as PHP-serialize. Paste the top row or two and I can decode.

**Working hypothesis based on the AJAX URL** (`/admin/commerce?ajax_form=1&_wrapper_format=drupal_ajax`) and it only failing on "Compare to prior period":

Drupal Commerce's overview dashboard has a Views-based summary block that computes deltas — this period vs prior period. When prior period has ZERO transactions (very likely on a sandbox where prod data is recent, no legit orders from a year ago), the aggregation math often trips one of:

- **Division-by-zero** in percentage-change calculation → PHP warning that Drupal escalates to 500
- **`array_map` / `array_combine` on empty result set** → `count mismatch` type error
- **SQL `AVG()` returning NULL** where the code expects a number → downstream type juggling fails

All three are known Drupal Commerce failure modes for the compare-to-prior-period widget on fresh/sparse data. The watchdog exception text will tell us which.

**Practical note:** since this fires only when there's insufficient prior-period data, and your sandbox is fed from prod dumps (which reflect prod's actual date distribution), the fix — if you even want one — is probably one of:

1. **Ignore it.** It's a Commerce module rough edge with sparse data; prod won't hit it because prod has years of actual data.
2. **Set the sandbox's system date closer to when prod data actually exists** — sandbox thinks "prior period" is a year with zero rows; if you shifted sandbox's clock back, "prior period" would land in the actual data window. Ugly and messy.
3. **Report/patch upstream in Drupal Commerce** — if you're feeling generous.

Would guess #1 is the right call. Curiosity-satisfaction — the watchdog query is the answer if you want to name it.
