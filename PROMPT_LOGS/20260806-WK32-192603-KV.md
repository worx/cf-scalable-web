**The `.load` file's own lexer is the problem, not pgloader's URL parser.**

Look at the file structure — pgloader `.load` files use comma as the WITH-clause option separator:
```
INTO postgresql://drupal_user:zMb9NjXhDpG,G6etCpf7A_qtNMBlg,yk@host/db?sslmode=require

WITH include drop,
     create tables,
     batch rows = 5000,
     ...
```

After envsubst embeds the raw password, the `INTO` line contains two literal commas. Pgloader's `.load` file parser almost certainly tokenizes on commas at the statement level BEFORE it hands the URL sub-string to its URL parser. So it might read a truncated password (up to first comma), leaving the trailing chars as syntactic garbage that either errors silently or gets dropped.

**Why this explains "worked before, failing now":**
`GenerateSecretString` does random draws. Comma isn't excluded, so ~1 in N generated passwords happens to have commas. Prior iterations rolled comma-free passwords; this one didn't. `psql` on the deploy-host works because libpq gets the URL directly — no `.load` lexer in the way.

**Why Path A is still right:** the `.load` file syntax uses commas structurally throughout. We can't escape or quote commas inside the URL portion without breaking pgloader's parser. Excluding commas from the generation policy is the right permanent fix.
