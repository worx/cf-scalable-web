fix(migration): parameterize MIGRATION_DB_NAME in run-pgloader.sh

Follow-up #2 to the DB-only test migration. Two things in one commit
because they touch the same code paths:

## 1. Fix schema-verify bug (Phase 6 was checking wrong schema)

`run-pgloader.sh:294` queried `information_schema.tables WHERE
table_schema='public'`, but pgloader creates a Postgres schema whose
name matches the source MySQL DB name (`zinew` here), NOT `public`. So
the verify always reported "0 tables" and a scary WARN even after a
perfect run:

    [INFO]  Target PostgreSQL 'public' schema now has 0 tables
    [WARN]  Target table count (0) is well below source (413).

Fix queries the correct schema.

## 2. Parameterize on MIGRATION_DB_NAME

Instead of hardcoding `zinew` in Phase 1's source precondition query,
Phase 3's confirmation message, and Phase 6's target verify, all three
now read `$MIGRATION_DB_NAME` (default `zinew`). Combined with the
already-parameterized `TEMPLATE_PATH`, a future migration of a
DIFFERENT MySQL database becomes:

  1. Author a new `<other>.load.tmpl` with `FROM mysql://.../<other>`
  2. Run: `MIGRATION_DB_NAME=<other>
          TEMPLATE_PATH=<repo>/migration/pgloader/<other>.load.tmpl
          make run-pgloader CONFIRMED=yes`

No script edits needed. Reusable wrapper.

The variable name `MIGRATION_DB_NAME` (not `SOURCE_DB_NAME`) is
deliberate: it is the name of the DB being migrated, which is used
for BOTH the source MariaDB db AND the target Postgres schema
(pgloader's default) — one string, two roles.

  - Startup log_info: reports MIGRATION_DB_NAME
  - Phase 1: source precondition query uses $MIGRATION_DB_NAME

       row expanding to the default when not overridden
