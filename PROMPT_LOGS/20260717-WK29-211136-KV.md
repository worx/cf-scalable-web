fix(logging): log_init must chmod 1777 an EXISTING dir too, not just new ones

Second live-caught bug from Kurt's migrate-full-all run:

    Phase 1: dispatch-restore-mysql
    tee: /var/log/worxco-migration/_ssm-run-deploy-host-restore-mysql-...log:
      Permission denied.

Cause: log_init's dir-creation block only invoked `chmod 1777` on the
sudo path — i.e., only when the caller couldn't mkdir and had to fall
back to `sudo mkdir + sudo chmod`. But a root caller (SSM's runner,
which runs as root) succeeds at plain `mkdir -p`, leaving the dir
`root:root 755`. Every subsequent ubuntu-side call (like Kurt's
tmux-inside-SSM shell running as ubuntu) then hits Permission denied
when tee tries to append.

## Fix

Two-step check now runs unconditionally:

  1. If the dir doesn't exist, create it (own uid first, sudo fallback).
  2. If the dir isn't writable by the current user, chmod 1777 (own
     first, sudo fallback, tolerant of failure).

Best-effort: if we can't chmod for any reason, the shell prints a
`WARN` on stderr and the script continues. tee's failure to open the
file is non-fatal — output still flows to stdout, just skips the log
file part. Same graceful degradation as before, just now with a
proactive fix attempt.

## Immediate fix for the running deploy-host

One-time on the current running deploy-host (safe to run WHILE
migrate-full-all is in progress — doesn't disrupt the running work):

    sudo chmod 1777 /var/log/worxco-migration

Then any future dispatcher call inherits a working dir.

## Files Modified

Tests: bash -n clean.

## Notes on the in-flight run

is non-fatal — it prints the error and continues copying stdin to
stdout. His tmux + Mac-side tee captures the full session. Remote
scripts self-log to S3 as designed. Only the Mac-side dispatcher's
per-run log file was skipped — that's the layer this commit repairs.
