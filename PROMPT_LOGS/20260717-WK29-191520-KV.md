## New scripts (scripts/deploy-host/)

### db-backup.sh <env> [db_name]

Snapshots a live PostgreSQL database by:
  1. GRANT app_user TO dbadmin (transient elevation)
  2. ALTER DATABASE <db> OWNER TO dbadmin
  3. Kick active connections (REVOKE CONNECT + pg_terminate_backend)
  4. ALTER DATABASE <db> RENAME TO <db>_backup_<UTC>
  5. CREATE DATABASE <db> OWNER <app_user>
  6. Restore backup DB ownership to <app_user>
  7. Restore CONNECT grants
  8. REVOKE app_user FROM dbadmin (undo transient elevation)

Post-run state matches pre-run role graph exactly — no persistent
membership grants. Prints the new backup DB name on stdout
(machine-parseable); status/progress on stderr.

### db-restore.sh <env> <source_backup_db> [target_db]

Rollback: drops target, renames source into place. Same transient
elevation dance. Same connection-eviction. Prompts operator to
run clear-drupal-cache after (to invalidate Valkey / on-disk
caches referencing pre-rollback state).

### db-list-backups.sh <env> [db_prefix]

Read-only listing of `<prefix>_backup_%` databases with owner and
size. Sorted newest-first (STAMP is ISO-ish so lexical = chronological).

## New Makefile targets

- `make db-backup ENV=<env> [DB=drupal] [CONFIRMED=yes]`
- `make db-restore ENV=<env> FROM=<backup_db> [DB=drupal] [CONFIRMED=yes]`
- `make list-db-backups ENV=<env> [DB=drupal]`

All deploy-host-only (require /etc/worxco/deploy-host-marker).
DB parameter defaults to 'drupal' since that's our current app DB;
override for future multi-DB scenarios.

## Design notes

- Scripts live in `scripts/deploy-host/` (top-level), not
  `migration/scripts/deploy-host/`. This is general-purpose DB
  management, not migration-specific — anyone wanting to preserve
  DB state before a destructive op should be able to use it.
- Confirmation prompt is default; `CONFIRMED=yes` skips it. Same
  pattern as existing destructive migration targets.
- App user (owner of the app DB) is sourced from
  `/etc/worxco/envs/<env>` via `DRUPAL_DB_USER`. Same source of
  truth as everything else on the deploy-host.
- Scripts use `psql-env <env>` for the DB connection (dbadmin master
  creds via Secrets Manager). No hardcoded credentials.
- Empty passes / no-op protections: refuses if source==target,
  refuses if target doesn't exist (would only rename source into
  place with `psql` directly).
