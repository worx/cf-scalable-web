### 14:38:22 - Response

Confirmed: `migrate-db-all` calls `dispatch-*` with `CONFIRMED=yes` bundled in. The bare `dispatch-restore-mysql` target doesn't set it — that's why it dies at Phase 2/6.

**Correct invocation for the timing test:**

```bash
time HOST_STACK=cf-migrate-host CONFIRMED=yes make dispatch-restore-mysql
time HOST_STACK=cf-migrate-host CONFIRMED=yes make dispatch-run-pgloader
```

Two things to note about that form:
1. **No `;` between the env var and `make`.** The `;` splits it into two statements; the env-var version dies as a standalone.
2. **`time` goes at the front.** `time` is a shell reserved word that wraps the whole pipeline that follows, so the env-var prefix inside it still reaches `make`.

Alternate belt-and-suspenders form (subshell — makes intent explicit):
```bash
(export HOST_STACK=cf-migrate-host CONFIRMED=yes; time make dispatch-restore-mysql)
```

Watch for `HOST_STACK = cf-migrate-host` in the log's "orchestrating" block on the next run — that's the tell that Phase 3's re-targeting is working. Then compare elapsed time against design-doc targets: restore ≤ 5 min, pgloader ≤ 12 min.

Also good to know — the small nuisance you hit (bare `dispatch-restore-mysql` needing `CONFIRMED=yes` to run non-interactively) is a pre-existing gap, not something Phase 3 introduced. Phase 4's `MIGRATE_HOST_LIFECYCLE` wrapper will hide all of this behind a single top-level command.
