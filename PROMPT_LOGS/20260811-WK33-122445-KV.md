### 12:24:45 - User Prompt

```
does it make sense to "make deploy-migrate-host &" (I could have my syntax wrong) so that it runs in the background, parallel to install-drupal-remote ?
```

---

### 12:25:30 - Response

Yes — the two are independent (deploy-migrate-host needs sandbox VPC + database, both up from deploy-all; install-drupal-remote needs compute + FSx + RDS, all also up from deploy-all; neither depends on the other). Save ~5-6 min of wall time.

The syntax is trickier than just adding `&` though, because `&` and `&&` don't compose the way you'd think. Also — there's already precedent in this repo for backgrounding parallel steps: `scripts/deploy-all-parallel.py` fans out AMI + database + cache into parallel jobs. Same pattern applies.

Correct shell form:

```bash
{
  make deploy-all ENV=sandbox || exit 1

  # Fan out: migrate-host CFN + install-drupal SSM + DNS UPSERT
  # all run in parallel. Migrate-host is the long pole (~5-6 min);
  # the other two finish before we wait for it.
  make deploy-migrate-host &
  MIGRATE_PID=$!

  make install-drupal-remote ENV=sandbox && make publish-dns ENV=sandbox
  FG_STATUS=$?

  wait $MIGRATE_PID
  MIGRATE_STATUS=$?

  [ $FG_STATUS -eq 0 ] || { echo "install-drupal or publish-dns failed"; exit 1; }
  [ $MIGRATE_STATUS -eq 0 ] || { echo "deploy-migrate-host failed"; exit 1; }

  cd migration && \
  HOST_STACK=cf-migrate-host make migrate-full-all-boosted ENV=sandbox AUTO=yes && \
  cd .. && \
  make smoke-test-public ENV=sandbox && \
  make destroy-migrate-host CONFIRMED=yes && \
  echo "=== FULL TEST CYCLE PASSED ==="
} 2>&1 | tee /tmp/full-test-$(date +%Y%m%d-%H%M%S).log
```

**Three real gotchas to know about:**

1. **Interleaved log output.** Both parallel jobs write to the same `tee`'d file. You'll see lines from deploy-migrate-host mixed with lines from install-drupal-remote. Grep-able but messy to read live.

   *If that bugs you*: tee each parallel job to its own log, then cat them serially at the end:
   ```bash
   make deploy-migrate-host > /tmp/mh.log 2>&1 &
   MIGRATE_PID=$!
   make install-drupal-remote ENV=sandbox > /tmp/id.log 2>&1
   ...
   wait $MIGRATE_PID; MIGRATE_STATUS=$?
   cat /tmp/mh.log /tmp/id.log
   ```
   Loses the live-monitoring appeal though.

2. **Silent failures on the backgrounded job.** If `deploy-migrate-host` fails in the background, `install-drupal-remote` still runs to completion (wasted ~5 min if you'd have aborted). Not a real problem — you still catch it before the migration step via the `$MIGRATE_STATUS` check — but you'll pay the wasted-work cost.

3. **`Ctrl-C` semantics get weird with backgrounded jobs.** If you interrupt the chain mid-run, the backgrounded `make deploy-migrate-host` may keep running as an orphan. You can add a shell `trap "kill $MIGRATE_PID 2>/dev/null" INT` right after the `MIGRATE_PID=$!` line to catch this.

Recommendation: **do the parallelization** — 5-6 min saved is real, and the failure modes are manageable. Use the separate-log-per-job form (#1 fix) if the interleaved output frustrates you. Skip the trap (#3) unless you're prone to Ctrl-C'ing test cycles.
