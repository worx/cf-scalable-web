Small correction on the plan — I was slightly wrong. Drupal's `system/files/...` route also needs a `file_managed` row registered in the DB for that URI. Without the DB migration, that route will 404 or 403 too, same reason as the report page. So `system/files` isn't the right test either.

Two better tests that don't need DB state:

## Test 1 — Direct S3 GET from your Mac (baseline)

Proves the file actually exists in the sandbox bucket + your credentials work:

```bash
aws --profile ZI-Sandbox s3 cp \
  s3://sandbox-drupal-media-kv-worxco/2025-09/branding.pdf \
  /tmp/branding.pdf && open /tmp/branding.pdf
```

Should download and open a small PDF. If yes → bucket/object confirmed.

## Test 2 — PHP-FPM's IAM instance role can talk to S3

This is the meaningful test: does the PHP-FPM worker (running under the compute IAM instance role) have the S3 permissions the flysystem module will need? Same nginx-served probe pattern we used for the env-var test:

```bash
# On deploy-host (or any box with FSx mounted):
sudo -u www-data tee /var/www/drupal/web/_s3-probe.php >/dev/null <<'PHP'
<?php
header("Content-Type: text/plain");
require "/var/www/drupal/vendor/autoload.php";
$bucket = getenv('AWS_S3_BUCKET');
echo "bucket = $bucket\n";
try {
  $client = new Aws\S3\S3Client([
    'region' => getenv('AWS_S3_REGION') ?: 'us-east-1',
    'version' => 'latest',
  ]);
  $r = $client->listObjectsV2(['Bucket' => $bucket, 'MaxKeys' => 3]);
  echo "list OK — first 3 keys:\n";
  foreach ($r['Contents'] as $o) echo "  " . $o['Key'] . "\n";
  $r2 = $client->headObject(['Bucket' => $bucket, 'Key' => '2025-09/branding.pdf']);
  echo "\nhead OK — 2025-09/branding.pdf size=" . $r2['ContentLength'] . " bytes\n";
} catch (Throwable $e) {
  echo "ERROR: " . get_class($e) . ": " . $e->getMessage() . "\n";
}
PHP

# Hit it (from an nginx box, same as env-probe):
# (SSM into an nginx box first, then:)
curl -sS -H "Host: sandbox.envs.zoning-info.com" http://localhost/_s3-probe.php

# Clean up (from any FSx-mounted box):
sudo rm /var/www/drupal/web/_s3-probe.php
```

Expected output:
```
bucket = sandbox-drupal-media-kv-worxco
list OK — first 3 keys:
  2025-09/FinalReport 47019.pdf
  2025-09/branding.pdf
  2025-10/BV ZV.pdf

head OK — 2025-09/branding.pdf size=431799 bytes
```

If both tests pass → S3 wiring is verifiably complete end-to-end (bucket exists, PHP-FPM sees the env, PHP has SDK access via instance role). All that's missing is the DB layer to *register* files as `s3://…` URIs.

If Test 2 errors with `AccessDenied` → the PHP compute instance role needs S3 grants on the media bucket. That'd be a cf-iam gap we'd fix. But that's a fairly unlikely miss.
