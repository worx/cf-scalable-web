- Error message rendered in Drupal chrome — Drupal handled the error
- 404 "Page not found" — route missing or entity gone
- 403 "Access denied" — permissions
- Page renders fully but a specific PDF/image link inside it is broken — file-level, not page-level

**2. What do the file URIs in the migrated DB look like?** This is the key question — does the DB reference `s3://...` (in which case flysystem_s3 should resolve it against our new bucket), or `public://...` (in which case it wants a local filesystem path that doesn't exist on sandbox's FSx)?

```bash
# On deploy-host:
psql-env sandbox -d drupal -c "
  SELECT uri, filesize, status
  FROM zinew.file_managed
  WHERE uri ILIKE '%.pdf'
  ORDER BY fid DESC
  LIMIT 10;
"
```

If uri comes back as `s3://YYYY-MM/whatever.pdf` → the S3 wiring we just did should be picking these up. We debug further.

If uri comes back as `public://YYYY-MM/whatever.pdf` or `private://...` → prod's DB stores files with the OLD scheme, and the s3:// stream wrapper never gets called for these entries. That would be a DB-content problem — the schemes would need updating (or flysystem needs to be configured as the `public://` scheme handler, not as a new `s3://` scheme).
