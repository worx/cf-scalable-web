feat(migration): AUTO=yes opts into auto-install-drupal on preflight fail

Kurt's operational reality check: migrate-full-all takes 2+ hours;
operators start it at end-of-day, come back in the morning. If the
Phase -1 preflight (commit 091f0eb) bails because Drupal wasn't
installed, that's 8-12 hours of wasted wall time — the operator's
gone home and nothing else happens overnight.

Fail-fast default is still the right posture for interactive runs
(operator right there, wants clear error, can fix and retry). But
for the fire-and-forget case, an opt-in "if you failed at preflight,
recover automatically" is the right escape hatch.

## Behavior

New env var: `AUTO=yes` on `make migrate-db-all` or `make migrate-full-all`.

  Preflight FAIL + AUTO not set (default)
    → bail with clear "run make install-drupal ENV=sandbox" hint
    → operator picks it up next interactive session
    → also lists the AUTO=yes and SKIP_PREFLIGHT=yes escape hatches
      right in the error output — no need to remember them

  Preflight FAIL + AUTO=yes
    → chain runs `make install-drupal ENV=sandbox` (~5-10 min via SSM)
    → re-runs preflight (should now pass — sanity check)
    → continues to Phase 0
    → total autonomy cost: ~10 min added to the front

  Preflight PASS
    → continues normally regardless of AUTO setting

## Why opt-in

The AUTO path bundles a HEAVY side effect (composer create-project,
drush site:install, secrets creation, nginx vhost publish) into what
was supposed to be a "copy prod data to sandbox" workflow. That
coupling is fine when the operator has explicitly opted in
("I'm going home; do what it takes to get me a working sandbox
by morning"), wrong when they haven't ("wait — I didn't ask you
to reset the sandbox").

## When to reach for it

- Overnight / fire-and-forget migrations
- CI / automated test pipelines building fresh sandboxes
- Any scenario where "come back to a failed run because a bootstrap
  step was skipped" is worse than the AUTO's implicit re-bootstrap

## When NOT to reach for it

- Interactive runs where operator wants explicit error and manual fix
- Any scenario where install-drupal's fresh-install side effects
  (rotating admin password, regenerating salt, dropping existing
  drupal-media state) would surprise a stakeholder — because AUTO
  will happily do all of that

  - Help block: AUTO=yes surfaced in the env-var section
  - Comments updated to document the fail-mode behavior

Tests: bash -n and make -n both clean; help output shows AUTO in
       the migrate-db-all / migrate-full-all env block

## For your sandbox after commit

The transition is designed to be backward-compatible — nothing breaks immediately. But to pick up the new SSM-based path on the running sandbox:

```bash
make ssm-deploy-host
cd ~/projects/cf-scalable-web && git pull
sudo make install-drupal ENV=sandbox
# → detects existing salt.txt, migrates it into SSM,
#   writes new settings.php that prefers env var,
#   file stays in sync as fallback

sudo refresh-env-config sandbox
# → populates DRUPAL_HASH_SALT in /etc/worxco/envs/sandbox
exit

# For PHP-FPM to pick up env[DRUPAL_HASH_SALT], the compute
# instances need to re-run configure-php.sh. Simplest:
make dispatch-restart-php-fpm ENV=sandbox   # or manually restart

# Or wait for the next natural instance rebuild.
```

Until you do those steps, the file fallback keeps everything working. After them, salt lives in Secrets Manager and file becomes redundant (but still there as safety net until we validate + follow-up removes it).
