### 12:11:54 - Response

Excellent question — and the answer changes my earlier analysis materially.

## Direct answer

**`aws s3 sync` (and `aws s3 cp`) between two S3 buckets uses `CopyObject` server-side by default. Data never touches the client.** The client is a pure API orchestrator:

1. Lists source bucket (paginated)
2. Compares against destination
3. Issues `CopyObject` API calls for new/changed objects
4. `CopyObject` tells S3 to copy source → destination *directly, inside AWS*
5. Only for single objects > 5 GB does it use MultipartCopy — still server-side

Client bandwidth flowing through the machine: **kilobytes of JSON API responses**, not the actual objects. A narrow-band network on the orchestrator is basically irrelevant.

**What DOES gate S3-to-S3 sync speed:**
- Number of objects (each = ≥1 API call — list + head + copy)
- Client's parallel-API-call concurrency (aws cli default = 10, tunable)
- S3's own throughput ceiling (3500 PUTs/sec per destination prefix — way higher than the client can push)

For a media library of ~50K files, that's ~250 sec of pure API work at 10 concurrent, ~50 sec at 40 concurrent. Bandwidth of the orchestrator doesn't matter.

## Two important implications for the earlier proposals

**A) sync-s3-media doesn't actually run on deploy-host.** I just checked: `sync-s3-media` SSM-dispatches to the **prod jumpbox** (migration/scripts/jumpbox/sync-s3-media.sh, Makefile line ~sync-s3-media header confirms `[FROM: Mac|deploy-host, PROFILE: ZI-Sandbox + ZoningInfoAdmin]` but the actual sync runs on the jumpbox). So the deploy-host 32 MB/s cap NEVER applied to sync-s3-media — it was never in that path.

**B) Your file-size intuition kills much of proposal #2.** If codebase is ~500 MB (many small files), private is empty, files is mostly empty, then:
- restore-codebase: ~500 MB / 32 MB/s = ~16 sec of pure bandwidth. Per-file latency probably drives it to 3-8 min for many small files.
- restore-files: near-empty, probably 1-2 min
- restore-private: empty, ~30 sec

**Total file-restore work: probably 5-10 min already.** Moving to migrate-host wouldn't save 10-15 min like I initially estimated — realistically **2-4 min at most**. The complexity (FSx mount + security group + HOST_STACK propagation) isn't worth that.

## What actually saved us with the RDS boost

The 44-min pgloader improvement worked because pgloader IS client-orchestrated — it reads from local MariaDB, transforms rows, writes to remote Postgres. The BOOST helped because RDS was the bottleneck on the write side, not because we moved the orchestrator. Different bottleneck class than what we're looking at here.

## Answer to your original question, restated

The narrow-band network on deploy-host / migrate-host / any host **doesn't affect S3-to-S3 sync speed at all** — that traffic is server-side. It **does** affect:
- S3 → local FSx transfers (restore-codebase, restore-files, restore-private)
- Anything reading/writing bytes through the client (pgloader before we boosted RDS, mysql dump downloads)

Since your biggest remaining chunk is either S3-to-S3 (server-side, not bandwidth-bound) or small-file FSx writes (per-file-latency-bound, not bandwidth-bound), **the deploy-host bandwidth story is largely a red herring for what's left.**
